How each reference was checked
- PostgreSQL: the case's PostgreSQL reference on world_cup at 127.0.0.1:55433 (see references-postgres-world-cup.txt).
- SQLite: the dump in backend/scripts/worldcup-rest-api/data materialised as rest.connector.ts materialises endpoints:
  one table per relation named by its key "api.world_cup.<table>", column affinity from the first non-null JSON value
  (number REAL, boolean INTEGER 1/0, string TEXT), every unquoted api.world_cup.<table> rewritten to the quoted key, as
  the connector does. Run on Python's sqlite3 (SQLite 3.51.0) and on better-sqlite3 (the engine the
  connector bundles, SQLite 3.53.4; script sqlite-run.js).
- Comparison: as backend/src/modules/sessions/result-compare.ts compares (the result-set match): same row count and
  column count, rows in any order, values normalised (numbers at 6 significant figures, text trimmed and case-folded).
- Static (static-checks.ts, with the repository's check modules): dialectProblem(sql, 'sqlite') finds nothing (R118);
  no FILTER, no DATE literal, no alias match (R205); every table reference is api.world_cup.<table>, a required table
  of the sample; the reference reads the same tables as the PostgreSQL one.
- Ported from the branch (feat/engine-eval-loop, suites/world-cup-rest.json), with the alias match renamed m in 7
  (busiest-stadium, semi-final-goals-2022, third-place-2022, booked-in-2022-final, mandzukic-goals-2018,
