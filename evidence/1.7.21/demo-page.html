Bug Fixes · roadmap 1.7.21

No orphaned backend survives the desktop app or an upgrade

on Windows a backend process sometimes outlives its window (crash, End task, sign-out) and keeps port 3000; the next launch or the upgraded version then talks to the stale backend.

In progress

Scope

  • (1) the backend exits within a few seconds when the desktop window process that spawned it is gone (DESKTOP_PARENT_PID)
  • (2) the desktop shell records the backend's PID in <APP_DATA_DIR>/backend.pid, stops a still-running backend from an earlier run at startup (only if it is the app's own executable), and the readiness probe accepts only the backend it just started (X-Backend-Instance header)
  • (3) a single-instance lock: a second launch focuses the running window
  • (4) the Windows installer and uninstaller force-stop every copy of Halo BI Assistant.exe the user runs, after the usual "close the app" check (frontend/build/installer.nsh).

Out of scope: freeing a port held by an unrelated program; macOS installers; the web / npx mode.

Acceptance

  • A backend whose parent process has died exits within about 2 s (unit test).
  • Startup stops a live process recorded in backend.pid when its image is the app's executable, leaves it alone otherwise, and clears a stale file (unit tests).
  • With another server answering on the backend port, the app does not report ready and records an error diagnostic naming the port.
  • Launching the desktop app a second time with the same profile opens no second window or backend and focuses the first.
  • The Windows installer built by build-desktop.yml compiles with the custom check.
