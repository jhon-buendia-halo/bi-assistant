# Synthetic eval domains

Databases the model has never seen, shaped like a customer's, with traps planted on purpose ([plan 3.4](../../plans/BA-9.md#34-synthetic-domain-databases-the-right-material-with-conditions)). Every row is invented by a seeded generator; nothing here describes a real company, person or patient. Each domain is a seedable sample in the Testing Data panel and a question set in the Evals tab.

## How a domain is built

The pattern every domain follows, in order. `<id>` is the kebab-case fixture id (`finance`), `<schema>` its snake_case schema (`finance`), `NNN` the next free number in the fixture folder.

1. **Brief and policy.** `docs/evals/domains/<id>.md`: the persona, the questions an analyst asks, a glossary with synonyms, the default filters, the metrics, and a trap table (what is planted where, which category it serves). `docs/evals/domains/<id>-policy.md`: one or two pages of business rules in words (fiscal year, what counts as completed, what is excluded). Both synthetic, no business review (decided 2026-10-13).
2. **Generator.** `docker/postgres/generate/<id>.ts`. Every value comes from one seeded `Rng` (`./lib/rng`), never `Math.random()` or today's date, so the same seed writes byte-identical SQL. It asserts every planted fact and throws rather than emit a fixture whose trap drifted. It writes two files:
   - `backend/src/modules/testing-data/fixtures/NNN_<schema>.sql`, the seed the app bundles (`nest-cli.json` copies `*.sql*` from that folder into `dist`). Not `docker/postgres/init/`: Compose runs that folder into the `world_cup` database on a fresh volume, while every domain gets its own database. Shape: a header comment, `BEGIN;`, `CREATE SCHEMA <schema>;`, `SET search_path TO <schema>, public;`, tables with identity keys, then views, `COMMIT;`. No psql meta-commands; the loader drops the schema first and replays the file in one transaction.
   - `backend/scripts/fixtures/<id>/facts.json`, the planted truths (the tie, the empty month, the test rows, the constant column), each with the number a reference query must return.
   Run it with `cd backend && npm run fixtures:<id>` (an npm script per generator: `npx ts-node -T -P tsconfig.json ../docker/postgres/generate/<id>.ts`). Keep the SQL under about 2 MB.
3. **Registry entry.** In `backend/src/modules/testing-data/fixtures/registry.ts`: id, name, description (one line, says "Synthetic"), `seedFile`, `schema`, `defaults: domainDefaults('<schema>')` (its own database on the shared server), datasource name `<Name> PostgreSQL`, dataset name `<Name>`, and `requiredTables` listing **every** table and view of the schema, so any reference may read any of them. Add the id to the order list in `testing-data.service.spec.ts`; `fixtures/registry.spec.ts` then checks that the seed creates the schema and every required entity.
4. **Question set.** `backend/src/mastra/evals/sets/<id>.json`, one variant `{ "id": "<id>", "fixtureId": "<id>", "dialect": "postgres", "caseIdPrefix": "" }` (Steps 2 and 3 add the Databricks and REST variants). Each case, by the recipe in [plan 3.2](../../plans/BA-9.md#32-how-to-write-a-question-that-holds-up):
   - `category`: one of the 18; at least five per main category in a new domain.
   - `split`: `held-out` for about 30% of each category, fixed when written; `dev` otherwise.
   - `tags`: `trap:<what is planted>` and `difficulty:easy|medium|hard`.
   - `question` in the persona's words, never a table or column name; `intent`: what it probes.
   - `notes`: the trap, the trap query (a plausible wrong SQL whose rows differ), the paraphrases (`Paraphrases: a | b`; the format has no field for them yet) and the `facts.json` entry the answer was checked against.
   - `checks`, each with a `criterion` from research 2.5: `calledTool run_readonly_sql` D1, `noToolErrors` D3, `includes` or `matches` on a fact in the prose G1; `calledTool ask_clarification` and `didNotCall run_readonly_sql` D5 on `ambiguous`; `didNotCall` G2 on `out-of-scope` and `non-existent`; `calledTool list_entities` and `didNotCall` I4 on `discovery`. One check of each type per case.
   - `expectedSql.postgres`: schema-qualified (`<schema>.<table>`), small result, every `ORDER BY` with a tie-break, no `LIMIT` that cuts a tie.
   Register the file in `backend/src/mastra/evals/eval-sets.ts` (an import and an `EVAL_SET_FILES` entry, after the existing domains) and add the set id to the order list in `eval-sets.spec.ts`.
5. **Run every reference before it counts.** Load the fixture into a database of your own through the Testing Data path (`TestingDataService.load`, or the panel), then `EVAL_SET=<id> EVAL_DATASETS="<Name>" npm run eval:validate`. Every reference must pass with at least one row; check each against `facts.json` where a planted fact applies, and run each trap query to see that its rows differ. Save the output as `evidence/1.1.7/references-<id>.txt`. A reference that fails or returns no rows is fixed, or the question is dropped.
6. **Dump.** `cd backend && npm run fixture:dump -- --fixture <id> [--database <db>]` writes `backend/scripts/fixtures/<id>/data/<relation>.json.gz` (a compact JSON array, gzipped; `gunzip -c` shows it) and a plain `_meta.json` with the fields of `backend/scripts/worldcup-rest-api/data/_meta.json` plus each relation's columns and types, for the Databricks loader (Step 2) and the REST server (Step 3). Views are dumped too, because the REST variant serves every required entity as an endpoint. Only the domains that run on Databricks and REST commit their dump (finance 0.44 MB, marketing analytics 0.16 MB; decided 2026-10-13); the domains copied from the branch run on PostgreSQL only and are dumped on demand.
7. **Specs.** A row in testing-data R2 and R4, the set in agents-evals R11 and its *Eval suite content*, the file in data-model 4.8, a row in the table above. The E2E list of sets in `frontend/e2e/agents.spec.ts` (`EVAL_SETS`) needs the new set and its question count.
