# Workflows

Every run runs a **workflow**: a fixed sequence of steps defined in code, each one deterministic code or a call to an agent. The catalogue holds five workflows: **Answer a Business Question** (`answer-business-question`; since 2026-11-13 eight steps, ten since 2026-11-15 with the optional Check data quality and Read images: it reads the reference images when the run has any, plans, then clarifies or analyses, validates, retries once and writes its answer) and, since 2026-11-13, **Assess Data Readiness** (`data-readiness-assessment`: it profiles one PostgreSQL or Databricks dataset, scores it with the deterministic engine, stores the report, looks up the rows behind its top findings and has the Data Readiness Agent explain it) and, since 2026-11-15, **Dashboard Image to Artifact** (`recreate-dashboard`: it reads the uploaded image of a dashboard into an interactive mock and saves it in Artifacts; R32) and **Map a Dashboard to Data** (`map-dashboard-data`: it maps a saved dashboard to the datasets the user picks and marks what the data cannot feed; R34) and, since 2026-11-16, **Review a Website** (`review-website`: it crawls a website and measures the visual and usability defects of every page on each screen size in a real browser, with the evidence of each finding; [../../system/agents.md](../../system/agents.md) 5.19). Agents are no longer workflows: they are a library ([../agents-evals/spec.md](../agents-evals/spec.md)) that workflow steps call (workflows → agents → skills → tools), and they cannot be run from the Workflows area or from their own page. Workflows are read-only: the app never creates, edits or deletes one (ADR-0040, partly superseded by ADR-0042).

Every workflow is a **run workflow**: it runs once on a typed input defined in code and shows each step's result on its page; no chat can start (ADR-0041). Every run is stored: it is listed, reopened with its result and files, and deleted with them. A workflow's page is a designer: its graph on a canvas and one Run panel beside it (the Chat), with no right panel. The Run panel streams the run live and shows the answer with its provenance, and the user can stop it, follow up on it and answer its clarifying question. The one-step agent workflows (`agent:*`), the Sequential test workflow (`seq-text-demo`) and Deep analysis (`deep-analysis`) were removed on 2026-11-12; the runs they stored stay readable (R23).

## Concepts

Defined in [../../product/glossary.md](../../product/glossary.md): workflow, code-defined workflow, agent, user agent, Live, session, workflow bar, workflow phase.

Capability-local vocabulary: a workflow's **id** (`answer-business-question`), the agent a code-defined workflow runs for (its **primary agent**), its **trigger** (`run`), a workflow's **input** (its typed fields), a **run** (one execution of a workflow on an input), a run's **context** (one earlier run whose question and answer it is given), the **run host** (internal: the in-memory session a run's agent turn executes on) and a **legacy run** (a stored run of a workflow that is no longer in the catalogue, R23).

## Rules

The catalogue
- R1. The workflow catalogue SHALL list exactly five workflows, in this order: **Answer a Business Question** (`answer-business-question`, owner `Official`), **Assess Data Readiness** (`data-readiness-assessment`, owner `Official`, since 2026-11-13), **Dashboard Image to Artifact** (`recreate-dashboard`, owner `Official`, since 2026-11-15) **Map a Dashboard to Data** (`map-dashboard-data`, owner `Official`, since 2026-11-15) and **Review a Website** (`review-website`, owner `Official`, since 2026-11-16; [../../system/agents.md](../../system/agents.md) 5.19). It SHALL NOT list any agent: no System, Official, draft-only or Live user agent has a workflow of its own (the Data Readiness Agent runs a step of Assess Data Readiness; it is not that workflow). Each entry SHALL carry its name, description, kind, owner, the agents its steps call, its number of steps, whether it takes the datasets the user picks, the datasets a session would take, the missing ones and the starter questions ([../../system/api.md](../../system/api.md) 116). The workflow is shown as "Answer a Business Question" (until 2026-11-13, "Questions to Insights v2", then the name of its agent, renamed on 2026-11-15 to Insights Analyst `insights-analyst`; the workflow's id was `qti-v2-turn` until then, data-model M16); a stored run keeps the workflow name it ran under, so an older run still reads "Questions to Insights v2" while sessions, whose `workflowRef.name` comes from the catalogue, show the new one.
- R2. The workflows' ids SHALL be `answer-business-question`, `data-readiness-assessment`, `recreate-dashboard`, `map-dashboard-data` and `review-website`. Any other id SHALL NOT resolve to a workflow, including the removed one-step ids `agent:assistant`, `agent:data-readiness`, `agent:<user-agent id>` and `agent:rfp`, and the removed `seq-text-demo` and `deep-analysis` (2026-11-12).
- R3. Workflows SHALL be defined in code. The app SHALL NOT offer any control that creates, edits, reorders or deletes a workflow or a step, and the API SHALL have no write route for workflows. Publishing, editing or deleting a user agent SHALL NOT change the catalogue.

Sessions
- R4. Every session SHALL run one workflow. A session created from this version on SHALL store the id of its workflow at creation and never change it. A session saved before SHALL have its workflow derived at every read: Answer a Business Question → `answer-business-question`; the Data Readiness Agent, a user agent (existing or deleted) and a plain session keep their internal `agent:<key or id>` reference as before (`agent:assistant` for a plain one), which is not in the catalogue and links to no workflow page; a session stored with `seq-text-demo` or `deep-analysis` reads as a plain Assistant session ([../../system/api.md](../../system/api.md) 2.1; [../../system/data-model.md](../../system/data-model.md) 3.4; [../past-chats/spec.md](../past-chats/spec.md) R65).

The Workflows pages
- R5. The **Workflows** area of the navigation rail ([../app-shell/spec.md](../app-shell/spec.md) R3) SHALL show the catalogue (R1) in one section, **Official**, with no **Mine** section. The workflow SHALL show its name, its description, its kind (`<n> steps`), `Uses <the names of the agents its steps call>` (Answer a Business Question: `Uses Michael, Zoe, Olivia, Sarah, Jessica`; Assess Data Readiness: `Uses Sarah, Zoe`), its missing datasets (`Missing dataset: <names>`) and **Run** (R12); it has no Start chat. The page SHALL say, under its heading, `Each workflow runs on an input. Its steps call agents, and agents use skills and tools.` A search SHALL filter the list by name or description, ignoring case; when nothing matches, the page SHALL say `No workflows match "<query>"`.
- R6. Retired (1.23.22). **Start chat** is gone from every workflow card and page: chats can no longer be started. `POST /sessions` with a `workflowId` is refused with `Workflow "<id>" runs on an input`, creating nothing ([../../system/api.md](../../system/api.md) 3). Past chats stay readable ([../past-chats/spec.md](../agent-answers/spec.md) R66).
- R7. Opening a workflow SHALL show its page as an n8n-style **designer** (since 1.23.10; left to right since the n8n-style page): a header with the breadcrumb `Workflows / <name>` (its first part goes back to the Workflows page), the name, id, kind and missing datasets, and no action; the workflow's **graph** on a canvas, left to right on one centre line (a Start node, one node per step with its title, id and kind badge `CODE` or `LLM`, an agent step's action, then its own agent's persona name and job title (Plan: Plan, Olivia, Analysis Lead; Analyse: Michael; Write answer: Write answer, Jessica, Insights Writer), its model and, when it has tools, one Tools sub-node (`<n> tools`) under it, an End node, and between them connectors labelled with the number of fields each passes on, as `GET /workflows/:id` returns them), fitted to the canvas when it opens (at most 100%, and at least 70% while the graph's full height shows, never below 40%; laid out roomy rather than packed, so Answer a Business Question opens at 70%, panned sideways, and a run pans to each node as it starts running), with zoom (50%–150%), reset and fit to screen, and **Execute workflow** at its top-right (R12); the canvas takes the column's full height (the **Logs** panel under it was removed on 2026-11-16: its list repeated the canvas and its detail the node dialog) and on the right one **Run** panel (resizable from its left edge, maximizable, folding to a narrow strip): in its header the run's status, `<n> of <m> nodes ran` (Start and End count), its duration and run id, and the run's activity line, and in its body the **Chat** (the question, the run's answer and the composer, R12, R13); while a run is shown each node carries its live state (R13) and a code step its run line, and once the run has ended **How it ran**, under the answer, reads it step by step. The app's right panel SHALL NOT be shown on a workflow's page (no `Expand right panel` button), and opening a workflow SHALL NOT open it; its open state is kept for the other views (app-shell R9). Clicking a node SHALL select it on the canvas; double-clicking it (or Enter) SHALL open its **node dialog**: its Input, its Parameters and Settings, and its Output in the run shown (Start: the description, trigger, output fields, input parameters and agents (R8); a step: id, kind, agent, model, tools, max steps, exits, what it receives and returns and the job description of the step's own agent: Olivia's for Plan, Michael's for Analyse, Jessica's for Write answer). A click, double click or Enter on the **Tools** sub-node SHALL open a keyboard-navigable list of its tools (Escape closes it), and picking a tool SHALL open that tool's dialog, not its agent step's: its name, description and input parameters (`GET /workflows/:id` `agents[].toolDetails`), its agent and step, and, in the run shown, each of its calls in that step with its input (the SQL) and result, their count, total duration and the run id; the agent's system prompt SHALL NOT appear in it. The Model sub-node SHALL open its agent step's dialog. Workflows SHALL stay the current rail item while the page is open. The agent detail's Graph tab keeps its own drawing ([../agents-evals/spec.md](../agents-evals/spec.md) R108).
- R8. A workflow's Start node dialog SHALL list, under **Agents**, each agent its steps call (for Answer a Business Question: Michael, Zoe, Nathan, Olivia, Sarah and Jessica; for Assess Data Readiness: Sarah and Zoe; for Dashboard Image to Artifact: Grace; for Map a Dashboard to Data: Daniel and Zoe), and an agent step's dialog SHALL link its own agent: its Agent link opens that agent's detail. Choosing one SHALL open that agent's detail ([../agents-evals/spec.md](../agents-evals/spec.md) R5).
- R9. The Workflows page SHALL read the catalogue each time it opens. Opening a workflow that is not in the catalogue SHALL show `Workflow "<id>" not found` on its page.
- R10. Retired (1.23.22). The Workflow tab no longer carries the workflow bar note (`In a chat, the workflow bar shows …`): no chat runs a workflow, so no bar follows it.

Run workflows
- R11. Every workflow SHALL have the trigger `run` (since 1.23.22; `chat` is gone). A workflow SHALL declare its input in code: typed fields, each with a name, a label, a type (`text`, `textarea` or `number`; R14 adds `boolean`, `datasets` and `dataset`), whether it is required and an optional placeholder. The catalogue SHALL carry each workflow's trigger and input ([../../system/api.md](../../system/api.md) 116). Running a workflow SHALL run its steps once along its flow (its edges, R27) on the input and answer each step's status (`success`, `failed`, `stopped` or `skipped`) and output, and the final output; a failing step SHALL make the run failed with that step's error, and the steps after it SHALL be skipped ([../../system/api.md](../../system/api.md) 118). A required field that is missing, empty or whitespace-only SHALL be refused with `<label> is required`, and a number field that is not a number with `<label> must be a number`, running nothing. A run SHALL NOT be a session: it writes no workflow bar and is never listed with the sessions; it is stored as a workflow run (R18). A workflow without input fields SHALL NOT be run (`Workflow "<id>" can't run on an input`), and no workflow can start a chat (`Workflow "<id>" runs on an input`, creating nothing).
- R12. A workflow's card SHALL show its kind (R5) and **Run**, which opens its page. A workflow's page SHALL show **Execute workflow** on its canvas, which unfolds the **Run** panel and focuses the composer's first control (the question), and never runs by itself: the Chat's **composer** (labelled `Input`) with one control per field (a text area, a text input or a number input, with its placeholder, marked required when required) and **Execute**, which reads `Executing…` and is disabled while the run is going. Its Start node dialog SHALL list the input fields as its input parameters (name, label, type, `required`), and Agents only when its steps call one.
- R13. After a run, the Run panel's Chat SHALL show the question asked (with a thumbnail for each reference image the run was given, R35), then `Run succeeded` or `Run failed: <error>` and the run's answer (for Answer a Business Question, with the query chips, the coverage line and the query rows of R31 in place of `How I worked this out` and `Data used`) or final output field by field; there SHALL be no per-step result cards and no separate run-progress list. Once the run has ended, **How it ran**, under the answer, SHALL read it step by step: the run's figures, then each step (Start and End aside) with its state, its duration and its story's headline, the title opening its dialog; while the run is shown, each node on the canvas SHALL carry its status as a badge (`×<n>` when it ran more than once), a code step its run line (its story's few words and its duration), each connector leaving a `Done` node SHALL be marked done, and each node's dialog SHALL show its Story and what the node received (its input) and produced in that run, its duration and, for an agent step, its tool calls; a failed node shows its error in its Output. A refusal SHALL be shown above the composer's buttons with the server's message (`Question is required`) or `Backend unreachable`. Running again SHALL replace the run shown, and leaving the page SHALL discard it, except a run still running or waiting for the user: leaving SHALL NOT stop it (R16; ADR-0048), and opening its workflow again SHALL show it once more, as it is then; a running run SHALL be followed again with its live view rebuilt from its events so far (the steps, the Thinking, each tool call, the answer forming; [../../system/api.md](../../system/api.md) 149) and go on live to its end. Opening a running run from Runs, or from its background task, SHALL do the same on its workflow's page. While it runs, every run (started here, resumed, or found running when the app starts, [../../system/api.md](../../system/api.md) 120) SHALL be a `workflow-run` background task (app-shell R58-R63), titled `<workflow name>: <question>`, `Waiting for you` while it waits, whose Open shows it as above and whose Stop stops it (150); its end is toasted only when the page does not show it, never for a stopped run.

Runs of Answer a Business Question (ADR-0041; backend only in 1.23.12)
- R14. The workflow SHALL declare its input in code, with the field types `text`, `textarea`, `number`, `boolean` (a checkbox; absent means false), `datasets` (one or more dataset names), `dataset` (exactly one) and `images` (reference images, up to 4; R35), each field optionally with a default, a datasource-kind limit and a hidden flag ([../../system/api.md](../../system/api.md) 116): Answer a Business Question takes `question` (at most 4000 characters), `images` (optional, R35) and `datasets`. A field MAY carry rules: `maxLength` (text), `min` and `max` (number). A run's input SHALL be checked as a whole, in field order, before anything runs (R24), every refusal reported (at most one per field): `<label> is required`, `Select at least one dataset`, `<label> must be a number`, `<label> must be at least <n>`, `<label> must be at most <n>`, `<label> must be at most <n> characters`, `<label> must be true or false`, `<label> must be PNG, JPEG or WebP images`, `<label> must be at most 5 MB each`, `<label> must be at most 4 images` (R35), `Dataset "<name>" not found`, `Dataset "<name>" is not a <kinds> dataset`; a missing, empty or whitespace-only required text (a blank question) SHALL be refused with `<label> is required`; unknown keys SHALL be ignored. The refusal SHALL carry the first error as its message and every error with the field it is about ([../../system/api.md](../../system/api.md) 118).
- R15. A run of Answer a Business Question SHALL run its steps on the run's input (R27), each Analyse attempt being an agent turn with the same model request a chat turn sent for the same question over the same datasets (plus the catalog and plan blocks): clarification, visuals and panel items SHALL behave as they did in a chat turn. Its answer SHALL be the Write answer step's text only; Plan's and Analyse's text SHALL NOT be streamed or stored as the answer, and no grounding guard or tool-only synthesis SHALL rewrite it. Its run host SHALL exist only for the run: created when it starts, never listed with the sessions, its memory thread deleted and itself discarded when it ends; its workspace stays with the run.
- R7a. An agent step on the workflow page SHALL show who does it as a person: the agent's portrait and an `AI` badge on its canvas node and, while a run is shown, what the agent is doing in place of its job title; the Run panel SHALL show the run's agents as a team, each with a first-person sentence about its part and the handoff from the agent before, built only from the run's step data, never by a model ([ui.md](../../system/ui.md) 4.4b, *Agents at work*). A step's queries SHALL stay reachable from its row through its dialog and the query inspector.
- R16. A streamed run SHALL report, in order: that it started (its run id), each step's start and end with its status (`running`, then `success`, `failed`, `stopped`, `suspended` for a step that waits for the user's answer (R28), or `skipped` for a step that never ran: the branch not taken, or the steps after a stop or a failure) and output, a step inside a loop (Plan and Clarify; Analyse and Validate) with its `attempt` (1, then 2 when it runs again), the agent turn's events exactly as the chat stream sends them (its `text` being the answer, streamed by Write answer), and one terminal event: the run with its answer, steps, output, datasets, panel items, visuals, or the chat stream's error for the same failure; a run that waits for the user sends the waiting step's `suspended` end and what it waits for (`input-required`) before the terminal event, the run then `suspended` ([../../system/api.md](../../system/api.md) 119, 138, 3.6). A refusal SHALL answer its real status before anything streams. A run (started or resumed) SHALL run on the server detached from the connection (ADR-0048): closing the connection, leaving the page, reloading or closing the window SHALL NOT stop it; each event SHALL carry its number (`seq`), and any client SHALL be able to follow the run again from its events so far, then live, until 10 minutes after it ends ([../../system/api.md](../../system/api.md) 149). **Stop** ([../../system/api.md](../../system/api.md) 150) SHALL stop it as Stop stops a chat turn: the agent turn aborts, nothing more of it is sent, the run ends `stopped` with any partial answer, and its stream ends with the stopped run; Stop on a run that ended answers it as it is. Try it (agents-evals R60) and a step's chat (R25) keep stopping when their connection closes.
- R17. A run MAY name one earlier run as its context: that run's question and answer SHALL reach the agent before this run's question, as a user and an assistant message, and nothing else of it; its own context SHALL NOT be carried, except that a follow-up SHALL carry the earlier run's reference images (R35) as its own `images`. The earlier run SHALL be read from the stored runs (R18), so it can be named after the app restarts. A context naming no stored run SHALL be refused with `Run "<id>" not found`, and one without an answer with `Run "<id>" has no answer to continue from`, except a run that waited for an answer it can no longer take (R28: **Run again with my answer**): its question and the clarifying question it asked (with its options, one `- <option>` line each) SHALL be the context, so the new run's question, the user's answer, is planned with the original question.

Stored runs (1.23.14; the run history UI is 1.23.21)
- R18. Every run of a workflow on an input, streamed (119) or not (118), SHALL be stored when it starts, as `running` with its workflow, the workflow's name, its checked input and its context, and updated when it ends with its status (`success`, `failed` or `stopped`), every step's status and output, its output or error and its question, answer, datasets, agent, panel items, visuals and the agent's saved phases ([../../system/data-model.md](../../system/data-model.md) 3.16). A stopped run (Stop, [../../system/api.md](../../system/api.md) 150; never a closed connection, R16) SHALL be stored `stopped` with any partial answer; a run that fails while ending SHALL be stored `failed` with that error. A run's workspace SHALL stay with the stored run, so its files can be downloaded after the run, and after a restart. A run's live state (its stop signal and event log) lives in server memory only: a backend restart still ends a running run as R20 says.
- R19. The Runs page's **Runs** tab (app-shell R46) SHALL show the run history and a row SHALL reopen its stored run (roadmap 1.23.21): a run whose workflow is still in the catalogue SHALL open on **its workflow's page, drawn with that run** (a run still running followed there live, R13; ADR-0048) (each node's status on the canvas, How it ran, the node dialogs with each step's input and output, the Run panel's Chat with its question, its answer or waiting card, its visuals, node chats and Follow up, as after a run on the page), the composer holding the run's input; a legacy run (R23) SHALL open read-only (`run-detail`, with no Run again). On the page, **Run again** (shown with a run, not while one runs) SHALL clear the run shown and open the composer with that run's whole input, its question too, to change and Execute as a new run; the run stays stored. The run history SHALL list every stored run, newest first, optionally one workflow's, each with its workflow, its status, its start and end, and a title: its question, else the workflow's first text input with a value, else the workflow's name, at most 120 characters ([../../system/api.md](../../system/api.md) 120). A stored run SHALL be readable with its full result, the panel items, workflow view and agent derived as a session's are (121), and its visuals and panel files SHALL download as a session's do (123-126). An unknown run SHALL answer `Run "<id>" not found` (HTTP 404).
- R20. Deleting a run SHALL remove it, its workspace and its files, its agents' memory threads (R30) and its node chats with their threads (R25) (122: `Run deleted`). A run still running SHALL NOT be deleted (`Stop the run before deleting it`). When the app starts, a run left `running` SHALL become `failed` with `The app stopped before the run finished`, keeping its workspace and its memory threads, and a run workspace that no stored run owns SHALL be deleted. The start-up clean-up of the agent editor's previews SHALL NOT touch run workspaces.

Runs from a workflow's page (1.23.15)
- R21. Every workflow (Answer a Business Question, Assess Data Readiness, Dashboard Image to Artifact and Map a Dashboard to Data) SHALL offer **Execute workflow** and the **Run** panel on their page (no Start chat). Before a run the Chat SHALL show the workflow's name with a hint and the workflow's starter questions as example chips (they fill the question and do not run). The composer SHALL have one control per input field the app does not set itself, by type: a text area (the question; Enter runs it, Shift+Enter adds a line), a text or number input, a checkbox for `boolean` (checked when its default is true), the dataset picker for `datasets` (picked datasets as chips, Add dataset opening a searchable list) and a list for `dataset` (the datasets of the field's datasource kinds); **Execute** and, while running, **Stop**. **New question** (shown with a run, not while it runs) SHALL clear the run shown and the question, keep the datasets (a run opened from Runs: its datasets and other fields) and focus the composer; **Run again** beside it keeps the question too (R19). Every run from the page SHALL stream ([../../system/api.md](../../system/api.md) 119): the status `Running…` in the Chat and each step's status live on its canvas node (`Running`, then `Done`, `Failed`, `Skipped` or `Stopped`), and inside a running agent step the agent's Thinking, each tool call with its rows and the answer forming in the Chat; when it ends, the run as stored: its status line and its answer as a chat shows one (text, reasoning, interpretation, data with its SQL, badges, visual, the clarification card), each step's data in its node dialog. **Stop** SHALL stop the run on the server ([../../system/api.md](../../system/api.md) 150) and drop the stream; the run reads `Run stopped`, its running step `Stopped`, and is then shown as stored, with any partial answer (Stop before the run has its id stops it as soon as it has one). Under a stored answer that is not a clarification the composer SHALL become the follow-up (Enter sends, `Follows up on this run`): **Follow up** SHALL start a run on the shown run's input with the new question and the shown run as its context (R17), saying `Follows up on “<earlier question>”`; picking a clarification option (or `Something else`, or Skip) SHALL do the same with the pick as the question. A refusal before the run starts SHALL show the server's message above the buttons (`Select at least one dataset`) and no result; a failure after it started SHALL read `Run failed: <error>`.
- R22. The answer in the Run panel's Chat SHALL offer the same rating as a chat answer ([../verified-queries/spec.md](../verified-queries/spec.md) R1-R7, R18; [../../system/api.md](../../system/api.md) 128): a thumbs-up saves the run's question and last successful SQL as a verified query, keyed by the run, and shows the toast `Answer saved as a verified query` and the `Verified` badge; a thumbs-down removes it. The rating is stored on the run's answer.

Legacy runs (2026-11-12)
- R23. A stored run whose workflow is no longer in the catalogue (the one-step `agent:*` workflows, `seq-text-demo` and `deep-analysis`) SHALL stay listed on the Runs tab and be deletable, like any run, and open read-only (`run-detail`, not on a workflow page) with its stored result, files, steps and answer (R19, R20). Its title SHALL be its question, else its first stored text input, else its workflow's stored name. It SHALL show its stored workflow name as plain text, with no link to a workflow page, no **Run again** (a run opens on its workflow's page only while `GET /workflows/<its workflowId>` resolves) and no follow-up (a run or follow-up on it answers `Workflow "<id>" not found`, 404), and its rating, if any, stays. A message's stored `report` stays readable (a stored deep-analysis message shows as a plain answer). A `answer-business-question` run whose `context` names a legacy run needs that run to have an answer, else it is refused with `Run "<id>" has no answer to continue from`. Nothing is migrated or deleted.

The input node (2026-11-12)
- R24. A workflow's input (its Start node) SHALL hold everything its steps need: every field a step requires SHALL be an input field or the output of an earlier step, with a compatible type, and the catalogue SHALL refuse to load a workflow that breaks this (the data contract's check, R26). Each input field SHALL say which steps read it straight from the input (`usedBy`, [../../system/api.md](../../system/api.md) 116). The input node SHALL validate the whole input before the workflow runs (R14): an invalid input SHALL be refused with every error at once, and no run SHALL be stored, no step run and nothing streamed. So no step has an exit for an invalid input: Receive question no longer fails on an empty question ([../../system/agents.md](../../system/agents.md) 5.11).

Node chats (2026-11-12)
- R25. After a run, the user SHALL be able to chat with an **agent step's** agent about that step's data in the stored run (a **node chat**): for Answer a Business Question, Plan, Analyse and Write answer (each with `insights-analyst` and its tools), Analyse after a retry as its last attempt. A node chat's turn SHALL be the agent alone, never a run of the workflow. Each turn SHALL give the agent, built by the backend from the stored run and never from the client: the workflow input, the step's status and error, its input and output as stored, its tool calls (tool, SQL or input, rows, error) and the run's final answer, at most 40 000 characters, saying so when something was shortened; plus the chat's earlier messages. The agent SHALL answer with its own tools, read-only, over the run's datasets, and its tool calls SHALL show with its answer. The chat SHALL be stored per run and step, read back when the run is reopened, and deleted with the run (R20). A node chat SHALL NOT change the run: its steps, output and answer stay as stored. A code step, a step the run did not reach or skipped, a run still running and a run of a workflow no longer in the catalogue (R23) SHALL NOT be chatted with ([../../system/api.md](../../system/api.md) 136, 137; [../../system/agents.md](../../system/agents.md) 5.16).

Data contracts between nodes (2026-11-13)
- R26. Every step's input and output SHALL be validated against its declared contract. Each step SHALL declare its input and output schema once, in code, and the field names, the JSON Schemas `GET /workflows/:id` serves and the workflow's `contractHash` SHALL be derived from them ([../../system/api.md](../../system/api.md) 117; [../../system/agents.md](../../system/agents.md) 5.12). When the catalogue loads, every required input field of every step SHALL be given by the closest earlier step's output (along the workflow's edges: a step on every path from Start to it), else by an input field, with a compatible type (the same JSON type; arrays of compatible items; objects with every required property given and compatible; an `unknown` field accepts anything), and never by an optional output or an optional input field without a default; a workflow that breaks this SHALL NOT load. When a run executes, each step's input SHALL be validated before it runs and its output after; a violation SHALL fail the step with `Contract violation in <Step title>: <path> <message>` (`<Step title> (input)` for its input; `<path>` dotted with indices, `(root)` for the whole value), the later steps SHALL NOT run and the run SHALL be `failed` with that error. Every stored run SHALL keep the `contractHash` of its workflow when it started ([../../system/data-model.md](../../system/data-model.md) 3.16).

The analyst flow of Answer a Business Question (2026-11-13)
- R27. Answer a Business Question SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.11): **Read images** first (R35: Zoe, the Image Reader, describes the run's reference images in one model call; `skipped` when the run has none), Receive question, Load catalog, **Interpret follow-up** (R36), then a **branch**: a follow-up over an earlier result SHALL take **Page result** and **Page answer** (R36); any other question SHALL take **Plan** (run by the System agent Olivia, `analysis-planner`: one model call, no tools, given each entity's columns and, when the run has images, Zoe's notes as text: the question restated, its measures, entities, scope and assumptions, and whether it must be clarified first; its assumptions SHALL be choices the analysis makes, never facts about the world, and each clarifying option SHALL be a measure the columns can compute), then a **branch**: when the plan needs clarification, **Clarify** SHALL make the run wait for the user's answer to the plan's clarifying question and its 2-4 options (R28), then go **back to Plan** with the answer, which plans the question with it and SHALL NOT ask again; otherwise the **analysis loop**: **Analyse** (the agent with its tools, given the plan and, when the run has images, Zoe's notes as text) then **Validate** (code: a query ran; no tool error left unresolved; no result cut at its row limit unless a later query re-aggregated; no answer resting on an arbitrary sample, a LIMIT reached with no sort, unless a later query read the whole data; the plan's measures found in the queries, as a warning that never fails), Analyse running **once more** with the failed checks when Validate fails, then, only when the run's input ticks **Check data quality** (`checkDataQuality`, a checkbox, off by default), **Check data quality** (the readiness engine assesses only the tables the last attempt's SQL read and stores the report, shown as the answer's readiness card; then Sarah, the Data Readiness Agent, in one model call without tools, picks the engine findings that could change or limit this answer, and each reaches Write answer as a failed finding `Data quality: <table>.<column> (<dimension>, <severity>)` with her sentence; a check that cannot run says so in a finding and never fails the run; otherwise the step is `skipped`), then **Write answer** (run by the System agent Jessica, `answer-writer`: one model call, no tools: the answer from the last attempt's result rows and the findings and, when the run has images, Zoe's notes as text, counts exact and derived figures rounded to at most 2 decimals, percentages to 1; an assumption only when it is one of the plan's choices and a caveat only when a result or a finding shows it; it reads the first 50 rows of each query, told how many the result has, and for a list of more rows than Write answer is shown (50) it writes a marker line `[[rows:<n>]]` that code SHALL replace with a Markdown table of that query's rows as stored (at most 200, with a note when the result has more), the marker never shown nor streamed) and **Wrap up**. An Analyse whose agent asks its own clarifying question SHALL make the run wait for the answer (R28), then run the agent again in the same attempt with the conversation so far and the answer (and any later attempt of the turn with it too); a stop ends the run there, with no answer written. `GET /workflows/answer-business-question` SHALL give the flow as edges (`next`, `branch`, `loop`, with their labels `Reference images` (Start to Read images, a branch), `No images` (Start to Receive question), `New question` and `Explore the earlier result` (after Interpret follow-up), `Needs clarification`, `Answered` (Clarify back to Plan), `Clear`, `Retry once`, `Valid or retried`) beside the step list, and the contract hash SHALL change with them ([../../system/api.md](../../system/api.md) 117). The instructions of Plan and Write answer SHALL open with `You plan a data analysis for Questions to Insights.` and `You write the final answer for Questions to Insights.` ([../../system/agents.md](../../system/agents.md) Appendix F).

- R29. Assess Data Readiness SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.13), on its input `dataset` (one PostgreSQL or Databricks dataset, required), `question` (optional; empty means `Assess the readiness of this dataset`) and `images` (optional, R35): **Read images** first (skipped when the run has none), **Resolve dataset**, **Profile source**, **Score readiness** and **Save report** (code, no LLM: the deterministic engine of [../data-readiness/spec.md](../data-readiness/spec.md) R6-R33 profiles the dataset's tables, scores them and stores the report with the run's id), **Rows behind findings** (code, no LLM, since 2026-11-16: one read-only query of the rows behind each of the report's top findings, each a source of the answer; a failed query is a failed source, never a failed run; data-readiness R34), then **Explain report** (the Data Readiness Agent, Sarah, reads the stored report and answers the question from it and, when the run has images, Zoe's notes as text; it SHALL NOT run a second assessment) and **Wrap up** (the report's id, overall score, band, finding count and the answer). Its edges SHALL be `next` edges from Start to End, with one `branch` from Start to Read images (`Reference images`) beside the `next` edge to Resolve dataset (`No images`). The run's answer SHALL carry the report's readiness card (data-readiness R5). A datasource that cannot be reached SHALL fail the run at Profile source with `Could not reach "<datasource>": <message>`, storing no report; a stop during Profile source SHALL end the run there, storing no report. It never waits for the user.

Human in the loop (2026-11-13; ADR-0043)
- R28. A run that needs the user's answer (Clarify, or Analyse's clarifying question, R27) SHALL be **suspended**, not ended: the waiting step `suspended`, the run `suspended` with what it waits for (the step, its title, the question, its options, since when, and until when it can be answered: 30 minutes), stored and listed as such, with only the steps that ran so far. Answering it (`POST /workflow-runs/:id/resume/stream` with the step and the answer, [../../system/api.md](../../system/api.md) 138) SHALL continue the **same run** from the waiting step, streaming as R16 (the steps keeping their ids and attempts; detached from the connection, its events numbered on), until it ends or waits again. Stop on a waiting run (150, e.g. from its background task) SHALL drop it as an expired one: stored `stopped` with what it waited for marked `expired`. A resume SHALL be refused before anything streams: an unknown run (404 `Run "<id>" not found`), a run not waiting (409 `Run "<id>" is not waiting for an answer`), a blank answer (400 `Answer is required`), another step (400 `Step "<stepId>" is not waiting for an answer`), and a run that can no longer continue (410 `This run can no longer continue — run it again with your answer`): one that waited more than 30 minutes, any waiting run once the app restarted, or one stored under another contract (its `contractHash` is not the workflow's, as for a run that waited before 1.28.8 moved Clarify under the question branch), which is then stored `stopped` with what it waited for marked `expired`. A run is resumed once per answer. A waiting run SHALL NOT be chatted with (409 `The run is waiting for an answer`, R25) nor visualized; deleting it drops it. A chat session (a past chat) keeps ending a turn on the clarification card. The Run panel's Chat SHALL show the waiting card with the question, its options and Continue, and for an expired run **Run again with my answer**, which runs again with the answer as the question and the expired run as its context (R17; [../../system/ui.md](../../system/ui.md) 4.4b).

Agents' history per run (2026-11-15)
- R30. Each agent of a run SHALL keep its conversation in a memory thread of that run ([../../system/agents.md](../../system/agents.md) 5.14): the agent that runs on the run's host (Analyse's Insights Analyst) in the host's thread, and each step agent with no memory of its own (Plan, Check data quality, Write answer) in a thread where each of its exchanges (its request and its reply) is recorded, without changing what that call sends the model. The threads SHALL outlive the run and go only with it (R20). A follow-up run (`context.fromRunId`) SHALL start from copies of the earlier run's threads, its own, and its Analyse SHALL go on in its copy with the earlier answer and the new question. A node chat SHALL keep its thread between turns, and its first turn about the step that ran on the run's host SHALL start from a copy of that thread (R25).
- R31. The answer of any workflow run whose answer holds queries (`data` records: Answer a Business Question, Assess Data Readiness, a user workflow) SHALL turn on the query inspector ([agent-answers](../agent-answers/spec.md) R67 to R78): a figure chip or a query row SHALL open the query in a non-modal sheet over the canvas, flush with the Run panel's left edge, at most 720 px wide and never over the Run panel; a maximized Run panel SHALL be restored first; opening another chip or row SHALL swap the query shown; the close button and Escape SHALL close it and give the focus back to the chip or row that opened it. When a stored answer with data is shown, the page SHALL build its evidence once per run id, in the background, and a failure SHALL be silent (the coverage line then shows no table sizes). The run detail page of a stored run (R19) SHALL host the same inspector for a run whose answer holds queries, as a sheet at the right of the page (at most 720 px, the same focus and Escape rules). A run whose answer holds no query keeps `How I worked this out` and `Data used` as before. The follow-up event answers a run stores (visual actions) carry no query, so they show no inspector.
- R32. Dashboard Image to Artifact SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.17), on its input `image` (one PNG, JPEG or WebP image of a dashboard, at most 5 MB, required) and `question` (the instructions, optional; empty means `Recreate this dashboard as an interactive mock`), through three steps in this order: **Load image** (code), **Read dashboard** (Grace, the Dashboard Reader, returns the dashboard as data: its filters, its widgets with their measures and breakdowns, and the columns of a mock dataset: the blueprint) and **Save dashboard** (code).
  - The run's result SHALL be an interactive visual of the run, drawn by a fixed runtime: no model SHALL write its markup, style or script. Every filter SHALL change the widgets it filters. It SHALL carry no mapping marks.
  - The run SHALL save the dashboard it read as an artifact (R33) named after the dashboard's title, with the image it was read from, and its answer SHALL list the widgets, name the artifact and point to Map a Dashboard to Data. A run that is stopped or fails SHALL save nothing.
  - Every value the dashboard shows SHALL be invented, and the answer SHALL say so. The run SHALL NOT read any datasource, and the dashboard SHALL NOT load any external resource.
  - The `image` field SHALL accept the image by paste (an image on the clipboard while the composer has focus) and by drop onto the composer, as well as by its file picker; a pasted or dropped image replaces the one chosen. This run has no Read images step (R35).
  - The image SHALL be stored as a file of the run's workspace and SHALL NOT be stored in the run's document nor returned by the API. An image that shows no dashboard SHALL fail Read dashboard with `The image shows no dashboard to recreate`. A follow-up on such a run SHALL run on the same image with the new instructions.
- R33. **Artifacts** SHALL be reusable context saved from workflow runs, kept in the **Artifacts** area of the navigation rail ([../app-shell/spec.md](../app-shell/spec.md) R3). The one kind today is a **dashboard**: the blueprint a Dashboard Image to Artifact run read (R32). An artifact SHALL NOT hold a data mapping.
  - A finished run of Dashboard Image to Artifact SHALL show that its dashboard was saved, with **Open** (the artifact's page) and **Map to data** (Map a Dashboard to Data with that artifact chosen).
  - The Artifacts area SHALL list every artifact grouped by kind, one section per kind that has artifacts, headed by the kind's plural (**Dashboards**) and the number of artifacts shown in it, newest first within a section; each artifact SHALL show its name, kind, description, number of widgets and filters and its image when it has one. A search over name and description SHALL filter the list, and a section with no match SHALL NOT be shown. An artifact's page SHALL show the dashboard drawn without mapping marks, and SHALL offer **Rename**, **Delete** (after a confirmation) and **Map to data**. Deleting an artifact SHALL NOT change the runs that used it.
- R34. Map a Dashboard to Data SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.18), on its input `artifact` (a dashboard saved in Artifacts, required), `datasets` (at least one, required) `question` (the instructions, optional; empty means `Map this dashboard to the datasets`) and `images` (optional, R35), through five steps in this order: **Read images** (skipped when the run has none; the flow branches to it from Start, R35), **Load dashboard** (code: the saved dashboard), **Load catalog** (code: the entities and columns of the datasets, names and types only), **Map data** (Daniel, the Data Mapper, ties each column the dashboard reads to a column of the datasets or says what is missing) and **Render dashboard** (code).
  - The run SHALL NOT read the artifact's image and SHALL NOT call the Dashboard Reader; only the reference images of R35, when the run has any, are read, by Zoe, and Map data gets her notes as text. Without a saved dashboard the run SHALL be refused with `Saved dashboard is required`; one that no longer exists SHALL be refused with `Artifact "<id>" not found`.
  - The run's result SHALL be the dashboard drawn by the same fixed runtime, in which every widget SHALL show its mapping status: **Mapped** when every column it reads has a source in the datasets, **Partly mapped** when some have, **No data** when none has. A widget with no data SHALL be visibly marked (a badge in words, not colour alone), and each widget SHALL list, per column it reads, its source or that it has none, with the reason. A filter with no source SHALL carry the same **No data** mark.
  - A source SHALL be shown only when its entity and column exist in the datasets' catalog: a source the model names that the catalog lacks SHALL count as missing. A status SHALL be counted from the checked sources, never taken from the model.
  - The run's answer SHALL explain the data mapping in detail: the result in numbers, how the mapping was done step by step, every widget and filter with its sources and the reason, and what the datasets lack.
  - Every value the dashboard shows SHALL be invented, and the dashboard and the answer SHALL say so. The run SHALL NOT read any row and SHALL NOT run any query. The mapping SHALL be kept in the run and SHALL NOT change the artifact.
- R35. **Reference images** (2026-11-15). Answer a Business Question, Assess Data Readiness and Map a Dashboard to Data SHALL each take an optional field `images` (label `Reference images`, type `images`; [../../system/api.md](../../system/api.md) 116): up to 4 PNG, JPEG or WebP images of at most 5 MB each, which the user attaches as context for the question, a chart or a report to compare with. A refusal SHALL read `Reference images must be PNG, JPEG or WebP images`, `Reference images must be at most 5 MB each` or `Reference images must be at most 4 images` (R14), running nothing. A run that was waiting for an answer (R28) from before this change SHALL still resume: its stored steps hold no notes, so it continues with none.
  - Each image SHALL be stored as a file of the run's workspace, `inputs/images/<n>.<ext>` (`n` from 1; `ext` `png`, `jpg` or `webp`), and the run's document SHALL hold only those paths, never an image's bytes; the run's list and detail SHALL NOT return the bytes either, but one image is served by path ([../../system/api.md](../../system/api.md) 151).
  - **Read images** SHALL be the first step of those three workflows, reached by a branch from Start (`Reference images`; the other edge from Start, `No images`, goes to the first step as before). When the run has no image the step SHALL be `skipped`, no model SHALL be called and no agent's request SHALL change: it is byte-for-byte what it was before this rule.
  - When the run has images, **Read images** (the System agent Zoe, the Image Reader, `image-reader`; [../../system/agents.md](../../system/agents.md) 2.15) SHALL describe all of them in one model call: for each image its kind, its title, what it shows, the figures and labels it carries and the text it shows. Her notes SHALL reach the later model steps (Plan, Analyse and Write answer; Explain report; Map data) as text only: no later step, agent or thread SHALL receive an image, and no image SHALL be recorded in any agent's thread or exchange. The notes SHALL be labelled as the user's context, never as data or instructions.
  - A model error in **Read images** SHALL fail the step and the run with the model's own error, and a stop SHALL end the run with no answer written. A reply that is not the expected shape SHALL NOT fail the run: each image reads `The Image Reader returned no description.`
  - A follow-up (R17) SHALL carry the earlier run's images and read them again, in one more model call; its stored input holds the same paths and any image added to the follow-up. **Run again** (R19) SHALL NOT carry the images, as it does not carry the `image` of Dashboard Image to Artifact: its form opens with the field empty.
  - The composer SHALL take images by an attachments control (**Attach images**), by paste (an image on the clipboard while a composer has focus) and by drop onto either composer, the run form and the follow-up form, up to 4 in all; a pasted or dropped text SHALL be left to the field it lands in. The Run panel's question and the run detail's Input SHALL show each image as a thumbnail ([../../system/ui.md](../../system/ui.md) 4.4b, 4.7.1).

A follow-up over an earlier result (2026-11-16, roadmap 1.28.8)
- R36. A run of Answer a Business Question whose question asks for another page, a filter or an order of an earlier answer's rows SHALL answer with that page instead of planning a new analysis ([../../system/agents.md](../../system/agents.md) 5.11).
  - **Interpret follow-up** SHALL make no model call when the run has no earlier queries: every first run, and every eval case. Otherwise Nathan (`result-explorer`, one model call, no tools) SHALL read the question against the earlier queries (a follow-up run's earlier answer, a chat's earlier answers), from the latest one's view.
  - A new question, a part that names no column of the result, or a model error SHALL plan the question as before: Interpret follow-up never fails the run. A stop during it SHALL end the run with no answer.
  - **Page result** SHALL read the page through the query inspector's page path ([../agent-answers/spec.md](../agent-answers/spec.md) R79-R84), recorded as an `explore_result` call of the run with its view, so the answer's query row SHALL open the inspector on that page. A page that cannot be read SHALL fail the step with its reason.
  - **Page answer** SHALL write the answer in code, with no model call: a headline in the inspector's words (`Rows 51–100 of 1,264`, `… matching` when filtered, `50,000+` when capped, `No rows match these filters.`), the query, `Understood as: <the request in words>`, a Markdown table of the page's rows and where the page sits. The run's stored answer SHALL keep the shape of any other run's.

## Edge cases and errors

- Opening a workflow that is not in the catalogue (unknown, draft-only, System or a primary agent) answers `Workflow "<id>" not found` (HTTP 404).
- Starting a chat with any workflow is refused with `Workflow "<id>" runs on an input`, whatever the id, creating nothing (R6).
- Starting a chat with a workflow in the catalogue is refused with `Workflow "<id>" runs on an input`, creating nothing (R6); an id that is not in the catalogue answers `Workflow "<id>" not found` first.
- A removed workflow id (`agent:assistant`, `agent:data-readiness`, `agent:<id>`, `seq-text-demo`, `deep-analysis`) answers `Workflow "<id>" not found` (HTTP 404) on read and on run. A user agent's draft preview (Try it) is not a workflow run ([../agents-evals/spec.md](../agents-evals/spec.md)).
- Running a workflow without input fields answers `Workflow "<id>" can't run on an input` (HTTP 400). Running Answer a Business Question without a question (or with a whitespace-only one) is refused with `Question is required`, and with a question but no datasets with `Select at least one dataset`; with neither, with both errors at once (R24). Running Assess Data Readiness on a dataset that is not PostgreSQL or Databricks is refused with `Dataset "<name>" is not a PostgreSQL or Databricks dataset` before the run (R29).
- A run whose agent turn fails ends with the chat stream's error for the same failure (a custom endpoint's `The endpoint rejected the API key (401)`); a stopped run sends nothing more. A run that asks a clarifying question is `suspended` until it is answered (R28): Clarify `suspended` when the plan asked it, Analyse `suspended` when the agent asked it; the steps after it have not run yet and are not listed.
- A resume of a run that is not waiting answers 409 `Run "<id>" is not waiting for an answer`; a blank answer 400 `Answer is required`; another step 400 `Step "<stepId>" is not waiting for an answer`; a run that waited more than 30 minutes, or any waiting run after a restart, 410 `This run can no longer continue — run it again with your answer` (the run is then `stopped`, `waitingFor.expired`), all before any SSE frame (R28).
- A plan the model returns as anything but the JSON object plans nothing (the question as is, no clarification), and a clarification with fewer than 2 options is dropped; an answer that is not the JSON object is taken as the answer text, its first line the headline (R27).
- An analysis whose second attempt still fails Validate is answered anyway: Write answer gets the failed findings and says what they limit (R27).
- A refused run (any R14 refusal, 404) stores nothing. A run of a workflow that has since been removed keeps its workflow's stored name and stays listed, readable and deletable (R23).
- Reading, deleting or downloading from a run that doesn't exist answers `Run "<id>" not found` (HTTP 404); a file the run never showed answers the session routes' errors (`Panel item "<id>" not found`). Deleting a run while it runs answers `Stop the run before deleting it` (HTTP 400) and keeps it.
- If the app stops during a run, the run is listed `failed` with `The app stopped before the run finished` after the next start; the files its turn had written stay downloadable.
- A step whose output breaks its contract fails with, for example, `Contract violation in Analyse: calls[2].rowCount Invalid input: expected number, received string`; one whose input breaks it fails before it runs with `Contract violation in Receive question (input): datasets Invalid input: expected array, received string`; a whole value of the wrong kind names the path `(root)` (`Contract violation in Analyse: (root) Invalid input: expected object, received string`). The steps after it are `skipped` and the run is `failed` with the same error (R26). An agent turn's own failure keeps its own error.
- A workflow whose step requires a field nothing gives, gives with another type, or gives only maybe (an optional output or an optional input field without a default) never loads: the backend refuses to start with `Workflow "<id>" breaks its data contract: <step>.<field> <problem>; …`, each problem `not given by the input or an earlier step`, `expected <a>, got <b>` or `may be missing` (R26).
- A run stored before contracts existed has no `contractHash`; it reads as before (R26).
- A node chat refuses, before anything streams or is stored: an unknown run (`Run "<id>" not found`, 404), a blank message (`Message is required`, 400), a run still running (`The run is still running`, 409), a run waiting for an answer (`The run is waiting for an answer`, 409), a run of a removed workflow (`Workflow "<id>" not found`, 404), an unknown or code step (`Step "<id>" has no agent to chat with`, 400), a step that did not run (`Step "<id>" did not run in this run`, 400), and a second message while a reply about the same step is still being written (409). A failed turn stores its error with the message; a stopped one stores what came, marked stopped.
