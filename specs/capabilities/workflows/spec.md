# Workflows

Every run runs a **workflow**: a fixed sequence of steps defined in code, each one deterministic code or a call to an agent. The catalogue holds five workflows: **Answer a Business Question** (`answer-business-question`; since 2026-11-13 eight steps, ten since 2026-11-15 with Read images and an optional step after Validate; since 2026-11-17 that step is Build visual, after Write answer: it reads the reference images when the run has any, plans (asking its own clarifying question first when the question is ambiguous), analyses, validates, retries once, writes its answer and charts it; since 2026-11-19 it is one line with no follow-up branch and no Clarify step, nine steps) and, since 2026-11-13, **Assess Data Readiness** (`data-readiness-assessment`: it profiles one PostgreSQL or Databricks dataset, scores it with the deterministic engine, stores the report, looks up the rows behind its top findings and has the Data Readiness Agent explain it) and, since 2026-11-15, **Dashboard Image to Artifact** (`recreate-dashboard`: it reads the uploaded image of a dashboard into an interactive mock and saves it in Artifacts; R32) and **Map a Dashboard to Data** (`map-dashboard-data`: it maps a saved dashboard to the datasets the user picks and marks what the data cannot feed; R34) and, since 2026-11-16, **Review a Website** (`review-website`: it crawls a website and measures the visual and usability defects of every page on each screen size in a real browser, with the evidence of each finding; [../../system/agents.md](../../system/agents.md) 5.19). Agents are no longer workflows: they are a library ([../agents-evals/spec.md](../agents-evals/spec.md)) that workflow steps call (workflows → agents → skills → tools), and they cannot be run from the Workflows area or from their own page. Workflows are read-only: the app never creates, edits or deletes one (ADR-0040, partly superseded by ADR-0042).

Every workflow is a **run workflow**: it runs once on a typed input defined in code and shows each step's result on its page; no chat can start (ADR-0041). Every run is stored: it is listed, reopened with its result and files, and deleted with them. A workflow's page is a designer: its graph on a canvas and one Run panel beside it (the Chat), with no right panel. The Run panel streams the run live and shows the answer with its provenance, and the user can stop it and answer its clarifying question (since 2026-11-20 the UI has no free follow-up: the composer shows only while no run is shown). The one-step agent workflows (`agent:*`), the Sequential test workflow (`seq-text-demo`) and Deep analysis (`deep-analysis`) were removed on 2026-11-12; the runs they stored stay readable (R23).

## Concepts

Defined in [../../product/glossary.md](../../product/glossary.md): workflow, code-defined workflow, agent, user agent, Live, session, workflow bar, workflow phase.

Capability-local vocabulary: a workflow's **id** (`answer-business-question`), the agent a code-defined workflow runs for (its **primary agent**), its **trigger** (`run`), a workflow's **input** (its typed fields), a **run** (one execution of a workflow on an input), a run's **context** (one earlier run whose question and answer it is given), the **run host** (internal: the in-memory session a run's agent turn executes on) and a **legacy run** (a stored run of a workflow that is no longer in the catalogue, R23).

## Rules

The catalogue
- R1. The workflow catalogue SHALL list exactly seven workflows, in this order: **Answer a Business Question** (`answer-business-question`, owner `Official`), **Answer a Business Question (orchestrated)** (`orchestrated-answer`, owner `Official`, since 2026-11-20; R45; [../../system/agents.md](../../system/agents.md) 5.22), **Assess Data Readiness** (`data-readiness-assessment`, owner `Official`, since 2026-11-13), **Dashboard Image to Artifact** (`recreate-dashboard`, owner `Official`, since 2026-11-15) **Map a Dashboard to Data** (`map-dashboard-data`, owner `Official`, since 2026-11-15), **Review a Website** (`review-website`, owner `Official`, since 2026-11-16; [../../system/agents.md](../../system/agents.md) 5.19) and **Consumption Gap Analysis** (`consumption-gap-analysis`, owner `Official`, since 2026-11-16; R37; [../../system/agents.md](../../system/agents.md) 5.20). It SHALL NOT list any agent: no System, Official, draft-only or Live user agent has a workflow of its own (the Data Readiness Agent runs a step of Assess Data Readiness; it is not that workflow). Each entry SHALL carry its name, description, kind, owner, the agents its steps call, its number of steps, whether it takes the datasets the user picks, the datasets a session would take, the missing ones and the starter questions ([../../system/api.md](../../system/api.md) 116). The workflow is shown as "Answer a Business Question" (until 2026-11-13, "Questions to Insights v2", then the name of its agent, renamed on 2026-11-15 to Insights Analyst `insights-analyst`; the workflow's id was `qti-v2-turn` until then, data-model M16); a stored run keeps the workflow name it ran under, so an older run still reads "Questions to Insights v2" while sessions, whose `workflowRef.name` comes from the catalogue, show the new one.
- R2. The workflows' ids SHALL be `answer-business-question`, `orchestrated-answer`, `data-readiness-assessment`, `recreate-dashboard`, `map-dashboard-data`, `review-website` and `consumption-gap-analysis`. Any other id SHALL NOT resolve to a workflow, including the removed one-step ids `agent:assistant`, `agent:data-readiness`, `agent:<user-agent id>` and `agent:rfp`, and the removed `seq-text-demo` and `deep-analysis` (2026-11-12).
- R3. Workflows SHALL be defined in code. The app SHALL NOT offer any control that creates, edits, reorders or deletes a workflow or a step, and the API SHALL have no write route for workflows. Publishing, editing or deleting a user agent SHALL NOT change the catalogue.

Sessions
- R4. Every session SHALL run one workflow. A session created from this version on SHALL store the id of its workflow at creation and never change it. A session saved before SHALL have its workflow derived at every read: Answer a Business Question → `answer-business-question`; the Data Readiness Agent, a user agent (existing or deleted) and a plain session keep their internal `agent:<key or id>` reference as before (`agent:assistant` for a plain one), which is not in the catalogue and links to no workflow page; a session stored with `seq-text-demo` or `deep-analysis` reads as a plain Assistant session ([../../system/api.md](../../system/api.md) 2.1; [../../system/data-model.md](../../system/data-model.md) 3.4; [../past-chats/spec.md](../past-chats/spec.md) R65).

The Workflows pages
- R5. The **User journeys** area of the navigation rail ([../app-shell/spec.md](../app-shell/spec.md) R3) SHALL show the catalogue (R1) in one section, **Official**, with no **Mine** section. The workflow SHALL show its name, its description, its kind (`<n> steps`, `1 step` for a one-step workflow), `Uses <the names of the agents its steps call>` (Answer a Business Question: `Uses Michael, Zoe, Olivia, Sarah, Jessica`; Assess Data Readiness: `Uses Sarah, Zoe`), its missing datasets (`Missing dataset: <names>`) and **Run** (R12); it has no Start chat. The page SHALL say, under its heading, `Each user journey runs on an input. Its steps call agent personas, and agent personas use skills and tools.` A search SHALL filter the list by name or description, ignoring case; when nothing matches, the page SHALL say `No workflows match "<query>"`.
- R6. Retired (1.23.22). **Start chat** is gone from every workflow card and page: chats can no longer be started. `POST /sessions` with a `workflowId` is refused with `Workflow "<id>" runs on an input`, creating nothing ([../../system/api.md](../../system/api.md) 3). Past chats stay readable ([../past-chats/spec.md](../agent-answers/spec.md) R66).
- R7. A workflow's page SHALL show, in its Builder view (R38; the page opens in Business by default), an n8n-style **designer** (since 1.23.10; left to right since the n8n-style page): a header with the breadcrumb `User journeys / <name>` (its first part goes back to the User journeys page), the name, id, kind and missing datasets, and no action; the workflow's **graph** on a canvas, left to right on one centre line (a Start node, one node per step with its title, id and kind badge `CODE` or `LLM`, an agent step's action, then its own agent's persona name and job title (Plan: Plan, Olivia, Analysis Lead; Analyse: Michael; Write answer: Write answer, Jessica, Insights Writer), its model and, when it has tools, one Tools sub-node (`<n> tools`) under it, an End node, and between them connectors labelled with the number of fields each passes on, as `GET /workflows/:id` returns them), fitted to the canvas when it opens (at most 100%, and at least 70% while the graph's full height shows, never below 40%; laid out roomy rather than packed, so Answer a Business Question opens at 70%, panned sideways, and a run pans to each node as it starts running), with zoom (50%–150%), reset and fit to screen, and **Execute user journey** at its top-right (R12); the canvas takes the column's full height (the **Logs** panel under it was removed on 2026-11-16: its list repeated the canvas and its detail the node dialog) and on the right one **Run** panel (resizable from its left edge, maximizable, folding to a narrow strip): in its header the run's status, `<n> of <m> nodes ran` (Start and End count), its duration and run id, and the run's activity line, and in its body the **Chat** (the question, the run's answer and the composer, R12, R13); while a run is shown each node carries its live state (R13) and a code step its run line, and once the run has ended **How it ran**, under the answer, reads it step by step. The app's right panel SHALL NOT be shown on a workflow's page (no `Expand right panel` button), and opening a workflow SHALL NOT open it; its open state is kept for the other views (app-shell R9). Clicking a node SHALL select it on the canvas; double-clicking it (or Enter) SHALL open its **node dialog**: its Input, its Parameters and Settings, and its Output in the run shown (Start: the description, trigger, output fields, input parameters and agents (R8); a step: id, kind, agent, model, tools, max steps, exits, what it receives and returns and the job description of the step's own agent: Olivia's for Plan, Michael's for Analyse, Jessica's for Write answer). A click, double click or Enter on the **Tools** sub-node SHALL open a keyboard-navigable list of its tools (Escape closes it), and picking a tool SHALL open that tool's dialog, not its agent step's: its name, description and input parameters (`GET /workflows/:id` `agents[].toolDetails`), its agent and step, and, in the run shown, each of its calls in that step with its input (the SQL) and result, their count, total duration and the run id; the agent's system prompt SHALL NOT appear in it. The Model sub-node SHALL open its agent step's dialog. Workflows SHALL stay the current rail item while the page is open. The agent detail's Graph tab keeps its own drawing ([../agents-evals/spec.md](../agents-evals/spec.md) R108).
- R8. A workflow's Start node dialog SHALL list, under **Agent personas**, each agent its steps call (for Answer a Business Question: Michael, Zoe, Olivia, Jessica and Ryan; for Assess Data Readiness: Sarah and Zoe; for Dashboard Image to Artifact: Grace; for Map a Dashboard to Data: Daniel and Zoe; for Consumption Gap Analysis: the Gap Advisor, Grace, the Requirements Analyst and the Layer Mapper), and an agent step's dialog SHALL link its own agent: its Agent link opens that agent's detail. Choosing one SHALL open that agent's detail ([../agents-evals/spec.md](../agents-evals/spec.md) R5).
- R9. The Workflows page SHALL read the catalogue each time it opens. Opening a workflow that is not in the catalogue SHALL show `Workflow "<id>" not found` on its page.
- R10. Retired (1.23.22). The Workflow tab no longer carries the workflow bar note (`In a chat, the workflow bar shows …`): no chat runs a workflow, so no bar follows it.

Run workflows
- R11. Every workflow SHALL have the trigger `run` (since 1.23.22; `chat` is gone). A workflow SHALL declare its input in code: typed fields, each with a name, a label, a type (`text`, `textarea` or `number`; R14 adds `boolean`, `datasets` and `dataset`), whether it is required and an optional placeholder. The catalogue SHALL carry each workflow's trigger and input ([../../system/api.md](../../system/api.md) 116). Running a workflow SHALL run its steps once along its flow (its edges, R27) on the input and answer each step's status (`success`, `failed`, `stopped` or `skipped`) and output, and the final output; a failing step SHALL make the run failed with that step's error, and the steps after it SHALL be skipped ([../../system/api.md](../../system/api.md) 118). A required field that is missing, empty or whitespace-only SHALL be refused with `<label> is required`, and a number field that is not a number with `<label> must be a number`, running nothing. A run SHALL NOT be a session: it writes no workflow bar and is never listed with the sessions; it is stored as a workflow run (R18). A workflow without input fields SHALL NOT be run (`Workflow "<id>" can't run on an input`), and no workflow can start a chat (`Workflow "<id>" runs on an input`, creating nothing).
- R12. A workflow's card SHALL show its kind (R5) and **Run**, which opens its page. A workflow's page SHALL show **Execute user journey** on its canvas, which unfolds the **Run** panel and focuses the composer's first control (the question), and never runs by itself: the Chat's **composer** (labelled `Input`) with one control per field (a text area, a text input or a number input, with its placeholder, marked required when required) and **Execute**, which reads `Executing…` and is disabled while the run is going. Its Start node dialog SHALL list the input fields as its input parameters (name, label, type, `required`), and Agents only when its steps call one.
- R13. After a run, the Run panel's Chat SHALL show the question asked (with a thumbnail for each reference image the run was given, R35), then `Run succeeded` or `Run failed: <error>` and the run's answer (for Answer a Business Question, with the query chips, the coverage line and the query rows of R31 in place of `How I worked this out` and `Data used`) or final output field by field; there SHALL be no per-step result cards and no separate run-progress list. Once the run has ended, **How it ran**, under the answer, SHALL read it step by step: the run's figures, then each step (Start and End aside) with its state, its duration and its story's headline, the title opening its dialog; while the run is shown, each node on the canvas SHALL carry its status as a badge (`×<n>` when it ran more than once), a code step its run line (its story's few words and its duration), each connector leaving a `Done` node SHALL be marked done, and each node's dialog SHALL show its Story and what the node received (its input) and produced in that run, its duration and, for an agent step, its tool calls; a failed node shows its error in its Output. A refusal SHALL be shown above the composer's buttons with the server's message (`Question is required`) or `Backend unreachable`. Running again SHALL replace the run shown, and leaving the page SHALL discard it, except a run still running or waiting for the user: leaving SHALL NOT stop it (R16; ADR-0048), and opening its workflow again SHALL show it once more, as it is then; a running run SHALL be followed again with its live view rebuilt from its events so far (the steps, the Thinking, each tool call, the answer forming; [../../system/api.md](../../system/api.md) 149) and go on live to its end. Opening a running run from Runs, or from its background task, SHALL do the same on its workflow's page. While it runs, every run (started here, resumed, or found running when the app starts, [../../system/api.md](../../system/api.md) 120) SHALL be a `workflow-run` background task (app-shell R58-R63), titled `<workflow name>: <question>`, `Waiting for you` while it waits, whose Open shows it as above and whose Stop stops it (150); its end is toasted only when the page does not show it, never for a stopped run.

Runs of Answer a Business Question (ADR-0041; backend only in 1.23.12)
- R14. The workflow SHALL declare its input in code, with the field types `text`, `textarea`, `number`, `boolean` (a checkbox; absent means false), `datasets` (one or more dataset names), `dataset` (exactly one) and `images` (reference images, up to 4; R35), each field optionally with a default, a datasource-kind limit and a hidden flag ([../../system/api.md](../../system/api.md) 116): Answer a Business Question takes `question` (at most 4000 characters), `images` (optional, R35) and `datasets`. A field MAY carry rules: `maxLength` (text), `min` and `max` (number). A run's input SHALL be checked as a whole, in field order, before anything runs (R24), every refusal reported (at most one per field): `<label> is required`, `Select at least one dataset`, `<label> must be a number`, `<label> must be at least <n>`, `<label> must be at most <n>`, `<label> must be at most <n> characters`, `<label> must be true or false`, `<label> must be PNG, JPEG or WebP images`, `<label> must be at most 5 MB each`, `<label> must be at most 4 images` (R35), `Dataset "<name>" not found`, `Dataset "<name>" is not a <kinds> dataset`; a missing, empty or whitespace-only required text (a blank question) SHALL be refused with `<label> is required`; unknown keys SHALL be ignored. The refusal SHALL carry the first error as its message and every error with the field it is about ([../../system/api.md](../../system/api.md) 118).
- R15. A run of Answer a Business Question SHALL run its steps on the run's input (R27), each Analyse attempt being an agent turn with the same model request a chat turn sent for the same question over the same datasets (plus the catalog and plan blocks): clarification, visuals and panel items SHALL behave as they did in a chat turn. Its answer SHALL be the Write answer step's text only; Plan's and Analyse's text SHALL NOT be streamed or stored as the answer, and no grounding guard or tool-only synthesis SHALL rewrite it. Its run host SHALL exist only for the run: created when it starts, never listed with the sessions, its memory thread deleted and itself discarded when it ends; its workspace stays with the run.
- R7a. An agent step on the workflow page SHALL show who does it as a person: the agent's portrait and an `AI` badge on its canvas node and, while a run is shown, what the agent is doing in place of its job title; the Run panel SHALL show the run's agents as a team, each with a first-person sentence about its part and the handoff from the agent before, built only from the run's step data, never by a model ([ui.md](../../system/ui.md) 4.4b, *Agents at work*). A step's queries SHALL stay reachable from its row through its dialog and the query inspector. Each agent's work SHALL show under that agent, in plain words (its own reason for each tool call, else a phrase for the tool, never the tool's name), with at most one step marked as under way, and the agents still waiting SHALL share one `Up next` line (2026-11-17).
- R16. A streamed run SHALL report, in order: that it started (its run id), each step's start and end with its status (`running`, then `success`, `failed`, `stopped`, `suspended` for a step that waits for the user's answer (R28), or `skipped` for a step that never ran: the branch not taken, or the steps after a stop or a failure) and output, a step inside a loop (Plan and Clarify; Analyse and Validate) with its `attempt` (1, then 2 when it runs again), the agent turn's events exactly as the chat stream sends them (its `text` being the answer, streamed by Write answer), and one terminal event: the run with its answer, steps, output, datasets, panel items, visuals, or the chat stream's error for the same failure; a run that waits for the user sends the waiting step's `suspended` end and what it waits for (`input-required`) before the terminal event, the run then `suspended` ([../../system/api.md](../../system/api.md) 119, 138, 3.6). A refusal SHALL answer its real status before anything streams. A run (started or resumed) SHALL run on the server detached from the connection (ADR-0048): closing the connection, leaving the page, reloading or closing the window SHALL NOT stop it; each event SHALL carry its number (`seq`), and any client SHALL be able to follow the run again from its events so far, then live, until 10 minutes after it ends ([../../system/api.md](../../system/api.md) 149). **Stop** ([../../system/api.md](../../system/api.md) 150) SHALL stop it as Stop stops a chat turn: the agent turn aborts, nothing more of it is sent, the run ends `stopped` with any partial answer, and its stream ends with the stopped run; Stop on a run that ended answers it as it is. Stop SHALL always end the run: when the work has not unwound 10 seconds after the stop, the run SHALL be stored `stopped` without it (its running steps `stopped`) and its stream ended with that run, and the work's later unwind SHALL NOT change that status (it may add the partial answer) and SHALL send nothing more. Try it (agents-evals R60) and a step's chat (R25) keep stopping when their connection closes.
- R17. A run MAY name one earlier run as its context: that run's question and answer SHALL reach the agent before this run's question, as a user and an assistant message, and nothing else of it; its own context SHALL NOT be carried, except that a follow-up SHALL carry the earlier run's reference images (R35) as its own `images`. The earlier run SHALL be read from the stored runs (R18), so it can be named after the app restarts. A context naming no stored run SHALL be refused with `Run "<id>" not found`, and one without an answer with `Run "<id>" has no answer to continue from`, except a run that waited for an answer it can no longer take (R28: **Run again with my answer**): its question and the clarifying question it asked (with its options, one `- <option>` line each) SHALL be the context, so the new run's question, the user's answer, is planned with the original question. A follow-up of Answer a Business Question MAY ask one step's agent alone instead of the whole workflow (R40). Since 2026-11-20 the app's UI no longer offers a free follow-up (no follow-up form, no agent picker): only the app itself sends this context, where it still applies, for an answer's clarification option and for **Run again with my answer** (R28); the API rule is unchanged.

Stored runs (1.23.14; the run history UI is 1.23.21)
- R18. Every run of a workflow on an input, streamed (119) or not (118), SHALL be stored when it starts, as `running` with its workflow, the workflow's name, its checked input and its context, its steps updated at each step change while it runs (the steps so far, the running one with its tool calls; a failed write of them never fails the run), and updated when it ends with its status (`success`, `failed` or `stopped`), every step's status and output, its output or error and its question, answer, datasets, agent, panel items, visuals and the agent's saved phases ([../../system/data-model.md](../../system/data-model.md) 3.16). A stopped run (Stop, [../../system/api.md](../../system/api.md) 150; never a closed connection, R16) SHALL be stored `stopped` with any partial answer; a run that fails while ending SHALL be stored `failed` with that error. A run that makes no progress SHALL be ended: a turn (119, 118, 138, Try it) that reports no event at all for 15 minutes (`WORKFLOW_RUN_IDLE_MINUTES`, at most 35791, the longest a timer holds; `0` turns it off) SHALL have its work aborted and be stored `failed` with `The run made no progress for <n> minutes and was stopped`, its running step failed with the same error, any partial answer kept, its stream ending with that error; it is never `stopped`, which is the user's Stop. A run waiting for the user is never timed. A run's workspace SHALL stay with the stored run, so its files can be downloaded after the run, and after a restart. A run's live state (its stop signal and event log) lives in server memory only: a backend restart still ends a running run as R20 says.
- R19. The Runs page's **Runs** tab (app-shell R46) SHALL show the run history and a row SHALL reopen its stored run (roadmap 1.23.21): a run whose workflow is still in the catalogue SHALL open on **its workflow's page, drawn with that run** (a run still running followed there live, R13; ADR-0048) (each node's status on the canvas, How it ran, the node dialogs with each step's input and output, the Run panel's Chat with its question, its answer or waiting card, its visuals, and node chats, as after a run on the page), the composer hidden while the run is shown (R21); a legacy run (R23) SHALL open read-only (`run-detail`, with no Run again). On the page, **Run again** (shown with a run, not while one runs) SHALL clear the run shown and bring the composer back with that run's whole input, its question too, to change and Execute as a new run; the run stays stored. The run history SHALL list every stored run, newest first, optionally one workflow's, each with its workflow, its status, its start and end, and a title: its question, else the workflow's first text input with a value, else the workflow's name, at most 120 characters ([../../system/api.md](../../system/api.md) 120). A stored run SHALL be readable with its full result, the panel items, workflow view and agent derived as a session's are (121), and its visuals and panel files SHALL download as a session's do (123-126). An unknown run SHALL answer `Run "<id>" not found` (HTTP 404).
- R20. Deleting a run SHALL remove it, its workspace and its files, its agents' memory threads (R30) and its node chats with their threads (R25) (122: `Run deleted`). A run still running SHALL NOT be deleted (`Stop the run before deleting it`). When the app starts, a run left `running` SHALL become `failed` with `The app stopped before the run finished`, keeping its workspace, its memory threads and the steps it finished, its running step (or a step stored waiting before the run was stored waiting) `failed` with the same error; every registered workflow's leftover suspended snapshots SHALL be deleted; and a run workspace that no stored run owns SHALL be deleted. The start-up clean-up of the agent editor's previews SHALL NOT touch run workspaces.

Runs from a workflow's page (1.23.15)
- R21. Every workflow (Answer a Business Question, Assess Data Readiness, Dashboard Image to Artifact, Map a Dashboard to Data, Review a Website and Consumption Gap Analysis) SHALL offer **Execute user journey** and the **Run** panel on their page (no Start chat). Before a run the Chat SHALL show the workflow's name with a hint and the workflow's starter questions as example chips (they fill the question and do not run). The composer SHALL have one control per input field the app does not set itself, by type: a text area (the question; Enter runs it, Shift+Enter adds a line), a text or number input, a checkbox for `boolean` (checked when its default is true), the dataset picker for `datasets` (picked datasets as chips, Add dataset opening a searchable list) and a list for `dataset` (the datasets of the field's datasource kinds); and **Execute**. The composer SHALL show **only while no run is shown** (2026-11-20): while a run is running, waiting for the user (a clarifying question or an approval gate) or ended, the conversation takes the whole column. **Stop** SHALL sit in the Chat's top bar, shown while a run is running. **New question** (shown with a run, not while it runs) SHALL clear the run shown and the question, keep the datasets (a run opened from Runs: its datasets and other fields) and bring the composer back, focused; **Run again** beside it keeps the question too (R19). Every run from the page SHALL stream ([../../system/api.md](../../system/api.md) 119): the status `Running…` in the Chat and each step's status live on its canvas node (`Running`, then `Done`, `Failed`, `Skipped` or `Stopped`), and inside a running agent step the agent's Thinking, each tool call with its rows and the answer forming in the Chat; when it ends, the run as stored: its status line and its answer as a chat shows one (text, reasoning, interpretation, data with its SQL, badges, visual, the clarification card), each step's data in its node dialog. **Stop** SHALL stop the run on the server ([../../system/api.md](../../system/api.md) 150) and drop the stream; the run reads `Run stopped`, its running step `Stopped`, and is then shown as stored, with any partial answer (Stop before the run has its id stops it as soon as it has one). The Chat SHALL NOT offer a free follow-up (decided 2026-11-20: "the follow-up question is useless since it was removed"): no `Follows up on this run` form, no follow-up question box, no agent picker (so no way to ask one agent alone, R40) and no **Follow up** button. Picking a clarification option (or `Something else`, or Skip) SHALL start a run with the pick as the question and the shown run as its context (R17), saying `Follows up on “<earlier question>”`. A refusal before the run starts SHALL show the server's message above the buttons (`Select at least one dataset`) and no result; a failure after it started SHALL read `Run failed: <error>`.
- R22. The answer in the Run panel's Chat SHALL offer the same rating as a chat answer ([../verified-queries/spec.md](../verified-queries/spec.md) R1-R7, R18; [../../system/api.md](../../system/api.md) 128): a thumbs-up saves the run's question and last successful SQL as a verified query, keyed by the run, and shows the toast `Answer saved as a verified query` and the `Verified` badge; a thumbs-down removes it. The rating is stored on the run's answer.

Legacy runs (2026-11-12)
- R23. A stored run whose workflow is no longer in the catalogue (the one-step `agent:*` workflows, `seq-text-demo` and `deep-analysis`) SHALL stay listed on the Runs tab and be deletable, like any run, and open read-only (`run-detail`, not on a workflow page) with its stored result, files, steps and answer (R19, R20). Its title SHALL be its question, else its first stored text input, else its workflow's stored name. It SHALL show its stored workflow name as plain text, with no link to a workflow page, no **Run again** (a run opens on its workflow's page only while `GET /workflows/<its workflowId>` resolves) and no follow-up (a run or follow-up on it answers `Workflow "<id>" not found`, 404), and its rating, if any, stays. A message's stored `report` stays readable (a stored deep-analysis message shows as a plain answer). A `answer-business-question` run whose `context` names a legacy run needs that run to have an answer, else it is refused with `Run "<id>" has no answer to continue from`. Nothing is migrated or deleted.

The input node (2026-11-12)
- R24. A workflow's input (its Start node) SHALL hold everything its steps need: every field a step requires SHALL be an input field or the output of an earlier step, with a compatible type, and the catalogue SHALL refuse to load a workflow that breaks this (the data contract's check, R26). Each input field SHALL say which steps read it straight from the input (`usedBy`, [../../system/api.md](../../system/api.md) 116). The input node SHALL validate the whole input before the workflow runs (R14): an invalid input SHALL be refused with every error at once, and no run SHALL be stored, no step run and nothing streamed. So no step has an exit for an invalid input: Receive question no longer fails on an empty question ([../../system/agents.md](../../system/agents.md) 5.11).

Node chats (2026-11-12)
- R25. After a run, the user SHALL be able to chat with an **agent step's** agent about that step's data in the stored run (a **node chat**): for Answer a Business Question, Plan, Analyse and Write answer (each with `insights-analyst` and its tools), Analyse after a retry as its last attempt. A node chat's turn SHALL be the agent alone, never a run of the workflow. Each turn SHALL give the agent, built by the backend from the stored run and never from the client: the workflow input, the step's status and error, its input and output as stored, its tool calls (tool, SQL or input, rows, error) and the run's final answer, at most 40 000 characters, saying so when something was shortened; plus the chat's earlier messages. The agent SHALL answer with its own tools, read-only, over the run's datasets, and its tool calls SHALL show with its answer. The chat SHALL be stored per run and step, read back when the run is reopened, and deleted with the run (R20). A node chat SHALL NOT change the run: its steps, output and answer stay as stored. A code step, a step the run did not reach or skipped, a run still running and a run of a workflow no longer in the catalogue (R23) SHALL NOT be chatted with ([../../system/api.md](../../system/api.md) 136, 137; [../../system/agents.md](../../system/agents.md) 5.16).

Data contracts between nodes (2026-11-13)
- R26. Every step's input and output SHALL be validated against its declared contract. Each step SHALL declare its input and output schema once, in code, and the field names, the JSON Schemas `GET /workflows/:id` serves and the workflow's `contractHash` SHALL be derived from them ([../../system/api.md](../../system/api.md) 117; [../../system/agents.md](../../system/agents.md) 5.12). When the catalogue loads, every required input field of every step SHALL be given by the closest earlier step's output (along the workflow's edges: a step on every path from Start to it), else by an input field, with a compatible type (the same JSON type; arrays of compatible items; objects with every required property given and compatible; an `unknown` field accepts anything), and never by an optional output or an optional input field without a default; a workflow that breaks this SHALL NOT load. When a run executes, each step's input SHALL be validated before it runs and its output after; a violation SHALL fail the step with `Contract violation in <Step title>: <path> <message>` (`<Step title> (input)` for its input; `<path>` dotted with indices, `(root)` for the whole value), the later steps SHALL NOT run and the run SHALL be `failed` with that error. Every stored run SHALL keep the `contractHash` of its workflow when it started ([../../system/data-model.md](../../system/data-model.md) 3.16).

The analyst flow of Answer a Business Question (2026-11-13)
- R27. Answer a Business Question SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.11): **Read images** first (R35: Zoe, the Image Reader, describes the run's reference images in one model call; `skipped` when the run has none), Receive question, Load catalog, then **Plan**. The workflow is **one line** (decided 2026-11-19: "the workflow will be linear, there will be no follow-up questions"): a follow-up run is always planned as a new question and never pages or filters an earlier result (R36 removed). **Plan** (run by the System agent Olivia, `analysis-planner`: one model call, no tools, given each entity's columns and, when the run has images, Zoe's notes as text: the question restated, its measures, entities, scope and assumptions, and, when the question can be read more than one way, **its own clarifying question** with 2-4 options; Plan asks in its own step, with no separate Clarify step: it SHALL make the run wait for the user's answer (R28) and, resumed with it, plan again with the answer and SHALL NOT ask twice; in a past chat's turn the question still ends the turn as the clarification card; its assumptions SHALL be choices the analysis makes, never facts about the world, and each clarifying option SHALL be a measure the columns can compute), then the **analysis loop**: **Analyse** (the agent with its tools, given the plan, each entity's columns as Plan gets them and, when the run has images, Zoe's notes as text) then **Validate** (code: a query ran; no tool error left unresolved; no result cut at its row limit unless a later query re-aggregated; no answer resting on an arbitrary sample, a LIMIT reached with no sort, unless a later query read the whole data; the plan's measures found in the queries, as a warning that never fails), Analyse running **once more** when Validate fails, with the failed checks and the queries attempt 1 ran (one line each, those a failed check flagged first, at most 8,000 characters) and at most 8 steps (attempt 1 has 15); Validate then checks the **kept** queries: the merged set (attempt 2's queries first, then attempt 1's that ran and that no failed check flagged; its checks read them in the order they ran, so a query of attempt 1 never resolves a problem attempt 2 left), or attempt 1's alone when the merged set fails a check attempt 1 passed, attempt 2 ran nothing successfully, or attempt 2 failed for any reason but a stop (a model error, the idle deadline, R43), which SHALL NOT fail the run and is recorded as the warning-only check `Retry completed (warning only)` (never a failed check nor a caveat; a stop still ends the run, and a failure of attempt 1 still fails it); then **Write answer** (run by the System agent Jessica, `answer-writer`: one model call, no tools: the answer from the kept queries' result rows and the findings and, when the run has images, Zoe's notes as text, counts exact and derived figures rounded to at most 2 decimals, percentages to 1; an assumption only when it is one of the plan's choices and a caveat only when a result or a finding shows it; it reads the first 50 rows of each query, told how many the result has, and for a list of more rows than Write answer is shown (50) it writes a marker line `[[rows:<n>]]` that code SHALL replace with a Markdown table of that query's rows as stored (at most 200, with a note when the result has more), the marker never shown nor streamed), then **Build visual** (R41; `skipped` when the run's input unticks **Build a visual**) and **Wrap up**. An Analyse whose agent asks its own clarifying question SHALL make the run wait for the answer (R28), then run the agent again in the same attempt with the conversation so far, the answer and the queries it ran before it asked (on a retry, after attempt 1's, in the one 8,000-character block; and any later attempt of the turn with the answer too); a stop ends the run there, with no answer written. `GET /workflows/answer-business-question` SHALL give the flow as edges (`next`, `branch`, `loop`, with their labels `Reference images` (Start to Read images, a branch), `No images` (Start to Receive question), `Retry once`, `Valid or retried`, `Build a visual` (Write answer to Build visual)) beside the step list, and the contract hash SHALL change with them ([../../system/api.md](../../system/api.md) 117). The instructions of Plan and Write answer SHALL open with `You plan a data analysis for Questions to Insights.` and `You write the final answer for Questions to Insights.` ([../../system/agents.md](../../system/agents.md) Appendix F).

- R29. Assess Data Readiness SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.13), on its input `dataset` (one PostgreSQL or Databricks dataset, required), `question` (optional; empty means `Assess the readiness of this dataset`) and `images` (optional, R35), in this order (since 2026-11-17): **Resolve dataset**, **Profile source** and **Score readiness**, **Read images** (skipped when the run has none: Zoe's reading starts once Resolve dataset has resolved the dataset and runs while it is profiled and scored; Read images awaits her notes, so a model error fails the run before anything is stored), **Save report** (code, no LLM: with the steps before it, the deterministic engine of [../data-readiness/spec.md](../data-readiness/spec.md) R6-R33 profiles the dataset's tables, scores them and stores the report with the run's id), **Explain report** (the Data Readiness Agent, Sarah, reads the stored report and answers the question from it and, when the run has images, Zoe's notes as text; it SHALL NOT run a second assessment), **Rows behind findings** (code, no LLM, since 2026-11-16: one read-only query of the rows behind each of the report's top findings, started at Save report and run while the agent explains, each a source of the answer ahead of the agent's own; a failed query is a failed source, never a failed run; data-readiness R34) and **Wrap up** (the report's id, overall score, band, finding count and the answer). Its edges SHALL be `next` edges from Start to End, with one `branch` from Score readiness to Read images (`Reference images`) beside the `next` edge to Save report (`No images`). The run's answer SHALL carry the report's readiness card (data-readiness R5). A datasource that cannot be reached SHALL fail the run at Profile source with `Could not reach "<datasource>": <message>`, storing no report; a stop during Profile source SHALL end the run there, storing no report. It never waits for the user.

A run that needs the user's answer (Plan's clarifying question, or Analyse's, R27) SHALL be **suspended**, not ended: the waiting step `suspended`, the run `suspended` with what it waits for (the step, its title, the question, its options, since when, and until when it can be answered: 30 minutes), stored and listed as such, with only the steps that ran so far. A note is not part of the workflow's contract: changing one leaves the contract hash as it was.
- R37. Consumption Gap Analysis SHALL run, fixed in code ([../../system/agents.md](../../system/agents.md) 5.20), on its input `datasets` (at least one, required: datasets whose schemas are tagged Landing, Normalized and Consumption), `question` (`Business questions`, required: one question per line, at most 20), `images` (`Reference dashboards`, optional, up to 4) and `artifact` (`Saved dashboard`, a dashboard saved in Artifacts, optional; empty means none), through eleven steps in this order (since 2026-11-17): **Resolve layers** (code; a dataset with no Consumption schema is refused before any model call), **Load layer catalogs** (code; it starts the lineage checks), **Read dashboards** (Grace reads every reference image as a dashboard, all at the same time; the saved dashboard is loaded without a model call), **Derive requirements** (the Requirements Analyst), **Infer lineage** (code; it takes the lineage checks, which ran meanwhile), **Confirm requirements** (waits for the user), **Map requirements** (the Layer Mapper), **Trace gaps**, **Probe evidence** (code), **Recommend fixes** (the Gap Advisor) and **Render report** (code).
  - The run SHALL have no Read images step (R35): its images are dashboards read by Grace. No schema tagged Consumption SHALL fail the run at Resolve layers with `No schema of the datasets <names> is tagged Consumption. Tag one in the dataset's schema notes (Datasets → schema → Layer).`; a question field with no question left SHALL fail it at Read dashboards with `Write at least one business question`.
  - Every question SHALL become one requirement (`Q1`…), and every widget that reads data and every filter of the dashboards one more (`W1`…, `F1`…), built in code from the dashboard's blueprint.
  - **Confirm requirements** SHALL make the run wait (R28) with the requirements and the option `Confirm the requirements`. That option (or an answer that confirms) SHALL keep them; any other answer SHALL be applied by the Requirements Analyst once, and the run SHALL go on without asking again.
  - Every requirement SHALL get one status, best first: **supported**, **derivable**, **grain**, **in Normalized only**, **in Landing only** or **missing**, taken from the sources checked against the catalogs and the inferred lineage, never from a model. A source the model names that the catalogs lack SHALL count as missing.
  - Lineage SHALL be inferred, never assumed (ADR-0051): candidate column pairs by name and type, each checked by a bounded read-only query of how many values match. The lineage checks and the probes SHALL be read-only queries recorded as sources of the answer, each with its rationale, so the query inspector opens them (R31); a query that fails SHALL be a source with its error, never a failed run.
  - The run's result SHALL be a report drawn by a fixed runtime (no model writes its markup), shown read-only on the run, and an answer written in code that never names a column the catalogs lack. Every fix SHALL start in the lowest layer that has the data, and its proposed change SHALL never be run.
  - A stop SHALL end the run at the step it reaches, `stopped`, storing no report.
- R38. **Business and Builder views** (2026-11-17). A workflow's page SHALL offer two views, picked in its header's **View** control ([../../system/ui.md](../../system/ui.md) 4.4b), Business first, for every workflow:
  - **Builder**, for people who build and debug workflows: the page as R7, R12 and R13 describe it (the canvas, the node dialogs and the Run panel with its Chat).
  - **Business**, for people who ask and read the outcome: an agentic chat. The Run panel's Chat alone, centred at full height, without the canvas or the Run panel: the conversation above (each question, the agents' thread (the team, R13) as they work, the status line, the answer forming, the answer view with its rating, visuals, scorecard and report, the Output of a run without an answer) and the composer at the bottom while no run is shown (the input form, R11, R14; no follow-up since 2026-11-20). **Every message SHALL run the workflow**: the question starts a run on the input, and a clarification option starts a new run with the shown run as its context (R17); New question and Run again bring the composer back, as in the Run panel. The Business view SHALL NOT show the live Thinking and tool calls or How it ran. Its answer SHALL keep the query inspector (R31). The Business view SHALL read a chain of runs (a clarification's pick, or a run stored as a follow-up) as **one conversation**: from the shown run it SHALL follow each run's `context.fromRunId` back (api.md 121, at most 20 runs; a deleted run ends it there) and show every earlier question and its answer above the shown one, oldest first, read-only, in place of the `Follows up on` line; a figure of an earlier answer SHALL open the query inspector on that earlier run. With two questions or more, the chat SHALL carry the **chat-history navigation** ([../../system/ui.md](../../system/ui.md) 3.8; Conversation, on the chat's right edge). A shown run SHALL show its **Execution ID** (R19's id to quote when reporting a run, copied on click), as Builder's Run panel does. **Open in Builder** (shown once a run is) SHALL switch to the Builder view on the same run, and an agent's See its data SHALL switch to Builder with that step's dialog open: the graph, each step's data and How it ran are read there.
  - Business SHALL be the view until one is picked, so a workflow page opens in it by default. The last view picked SHALL be kept on the device (`localStorage` `qti.workflow-view`) and every workflow page SHALL open in it. Switching views SHALL keep the shown run, its input and any run in progress.

- R39. **Agent personas are named with their role** (2026-11-17). Wherever the app names an agent persona inside a user journey, it SHALL show the persona's role (its job title, `role` in api.md 116 and 117 and on each agent step) next to its name, and the name alone when the persona has none: the agents' thread of a run (`Jessica · Insights Writer · Write answer`), a node dialog's agent line (`Michael, Insights Analyst · ≤ 15 steps`) and its `Chat with Michael, Insights Analyst`, the Start node's Agent personas list, a step's and a tool's Agent persona field, and a user journey card's `Uses Michael (Insights Analyst), …`. The canvas node already shows the role under the name (ui.md 4.4b). Sentences that only refer to a persona already introduced (a handoff `Nathan passed … to Olivia`, a step's story) keep the name alone.

- R43. **Model calls survive one transient failure** (2026-11-17; [../../system/agents.md](../../system/agents.md) 1.6). Every model call a workflow step makes SHALL have a deadline, and the run's Stop SHALL stop it at once, never retried and never reported as a timeout.
  - A step's single model call (Plan, Write answer, Read images, Read dashboard, Map data, Derive requirements, Confirm requirements, Map requirements, Recommend fixes, Review templates) SHALL be aborted past its deadline, 5 minutes per try (10 when its reply may take 16,000 tokens or more, Map requirements; Iris's 2 minutes, in her own words: agents.md 5.19), and the step SHALL fail saying the model did not answer in time; in Review templates, a timeout SHALL instead record that template as not reviewed (the last item below).
  - Such a call SHALL be tried once more, after 2 s, when it failed on the network with no HTTP status or with status 408, or when its reply was cut at the output limit, and the retry SHALL send the same request and show one line in the running step's thinking. A status the app's fetch layer already retries ([../llm-settings/spec.md](../llm-settings/spec.md) R31) and a timeout SHALL NOT be tried again; a second failure SHALL fail the step. Nathan's call has the deadline only.
  - A reply cut at the output limit SHALL be told apart from an off-shape reply: a reply read as data that is cut twice SHALL fail the step with a message naming the step and the limit, never as an empty result. Write answer SHALL be tried again only while nothing was shown; cut after its text was shown, it SHALL keep that text, add `The answer was cut at the output limit.` and succeed.
  - A streamed agent step (Analyse, the one-step Answer, Explain report) SHALL fail when the model sends nothing for 5 minutes while none of its tool calls is running; it has no total limit and is not tried again, so a long analysis on a slow warehouse keeps going while it streams. On the retry of Analyse (attempt 2) that failure SHALL NOT fail the run: it is recorded as the retry's error and the run keeps attempt 1 (R27). A clarifying question SHALL still stop only the attempt.
  - Review templates SHALL go on when Iris cannot review a template: that template SHALL be recorded as not reviewed with the reason and no findings, the other templates SHALL still be reviewed, and the step SHALL fail, with the first error, only when no template was reviewed. The report and the answer SHALL say how many of the templates Iris reviewed and show `not reviewed: <reason>` on that template; a stored run from before renders as it did.

- R44. **Approval gates and clarifying questions** (2026-11-19; [../../system/agents.md](../../system/agents.md) 5.11 *Interactive runs*, [../../system/api.md](../../system/api.md) 138). A run of Answer a Business Question whose input ticks **Approve each step** (`approveSteps`, a checkbox, ticked by default, labelled `Approve each step: every agent's work waits for your OK`; no step reads it, as with `buildVisual`) SHALL be **interactive**. A past chat's turn and an eval SHALL NOT be interactive. In an interactive run:
  - Each step agent's outcome that goes on to another agent SHALL wait for the user's approval before it is handed on: **Read images** (Zoe's notes, always when she ran); **Plan** (a clear plan; a plan that needs clarification waits on its own question instead, in the same step, and the plan made with the answer then waits on this gate); **Analyse** (each attempt that did not ask and was not stopped, before Validate and Jessica); **Write answer** (only when Build visual runs after it: her answer SHALL NOT be streamed until approved and, once approved, SHALL be delivered as the run's answer). **Build visual** (Ryan; only when he built a visual, which has a `visualId`: none when the design failed or was skipped) is last and waits on the gate below, whose approval ends the run (Wrap up).
  - The wait SHALL be the same suspension as a clarifying question (R28; ADR-0043; [../../system/api.md](../../system/api.md) 138): `waitingFor` with the `question` `<Agent>'s <thing> is ready. Approve it to hand it to <next>, or write what to change.`, `options` `['Approve']` and `review`, the outcome in words (Markdown): Zoe's notes; Olivia's plan as Question, Measures, Entities, Scope and Assumptions; Michael's queries with their rationale and row counts, and his note; Jessica's answer. The run's card for it is the approval card ([../../system/ui.md](../../system/ui.md) 4.4b).
  - Resumed with `Approve` (or ok, okay, yes, approved, lgtm, aprobar, aprobado, sí, si; case-insensitive, with an optional full stop), the held outcome SHALL be passed on unchanged with no new model call. Any other answer SHALL be a **revision**: the same agent SHALL be called again with its earlier reply and the user's words (Analyse: in the same attempt, with the gate's question and the words as the answered question), and the new outcome SHALL wait on the gate again.
  - Zoe and Jessica MAY first ask the user **one clarifying question**: their request ends with the clarify rule, and the reply is the JSON `{"clarification": {question, options}}`. The step SHALL wait (suspend kind `clarify`) and, once answered, call the agent again with the question and the answer and not offer the rule again. Olivia keeps asking in her own Plan step (no Clarify step) and Michael through `ask_clarification`, as before. Ryan SHALL NOT ask first: he is the last agent and his reply is a visual spec; his gate is where the user steers him.
  - **Build visual's gate** (2026-11-19; [../../system/api.md](../../system/api.md) 138). Once Ryan built a visual, the run SHALL wait with the `question` `Ryan's visual is ready. Approve it to finish the run, or write what to change (a filter, another chart, a detail) and attach reference images if you want.`, `options` `['Approve']`, a `review` of the visual's title in bold and `Open it to check it before you approve it.` (preceded by `**The change could not be made:** <error>` after a failed change) and the **`visualId`** of the visual. While the run waits, the visual SHALL be openable (the suspended run carries the host's `visualizations`). `Approve` with no images ends the run. Any other words, or **reference images**, SHALL be a revision that makes Ryan produce a **new version of the same visual** (`VisualizationService.update`, the tailor path, with the words as the instruction; the workflow's step model applies), and the run SHALL wait on his gate again. When images came, Zoe SHALL first read them and her notes SHALL be the designer's `<reference>`. Images with no words use the instruction `Follow the reference images the user attached.` A change that fails SHALL keep the visual as it was and say why on the gate.
  - **Reference images.** Resuming Ryan's gate MAY carry up to 4 images (PNG, JPEG or WebP, 5 MB each; api.md 138), accepted only while `waitingFor.visualId` is set. They SHALL be written to the run's workspace at `inputs/revisions/<round>-<n>.<ext>` before the run resumes and handed to the step as their paths. The answer MAY be blank when images are sent.
  - Outside an interactive run every request and reply SHALL be exactly as before.
  - The suspend payload (`kind`, `question`, `options`, `review`, `outcome`, `reply`) SHALL be held in the run's snapshot; only `question`, `options` and `review` SHALL reach `waitingFor`.
  - **Model** (2026-11-19; [../../system/agents.md](../../system/agents.md) 1.3). The step agents of the workflow SHALL run on `claude-opus-5-5` at reasoning effort `medium` when the saved model is served as a Claude model, in runs and in past chats, never in evals; otherwise on the saved model and effort.

- R45. **Answer a Business Question (orchestrated)** (2026-11-20; `orchestrated-answer`; [../../system/agents.md](../../system/agents.md) 5.22). The workflow SHALL be a second version of Answer a Business Question in which a **supervisor agent** (the orchestrator) will decide at run time which agents to call (Zoe, Olivia, Michael, Jessica and Ryan, as its tools), instead of a fixed line of steps. **Today it is an empty shell**, with the orchestrator not built yet:

## Edge cases and errors

- Opening a workflow that is not in the catalogue (unknown, draft-only, System or a primary agent) answers `Workflow "<id>" not found` (HTTP 404).
- Starting a chat with any workflow is refused with `Workflow "<id>" runs on an input`, whatever the id, creating nothing (R6).
- Starting a chat with a workflow in the catalogue is refused with `Workflow "<id>" runs on an input`, creating nothing (R6); an id that is not in the catalogue answers `Workflow "<id>" not found` first.
- A removed workflow id (`agent:assistant`, `agent:data-readiness`, `agent:<id>`, `seq-text-demo`, `deep-analysis`) answers `Workflow "<id>" not found` (HTTP 404) on read and on run. A user agent's draft preview (Try it) is not a workflow run ([../agents-evals/spec.md](../agents-evals/spec.md)).
- Running a workflow without input fields answers `Workflow "<id>" can't run on an input` (HTTP 400). Running Answer a Business Question without a question (or with a whitespace-only one) is refused with `Question is required`, and with a question but no datasets with `Select at least one dataset`; with neither, with both errors at once (R24). Running Assess Data Readiness on a dataset that is not PostgreSQL or Databricks is refused with `Dataset "<name>" is not a PostgreSQL or Databricks dataset` before the run (R29).
- A run whose agent turn fails ends with the chat stream's error for the same failure (a custom endpoint's `The endpoint rejected the API key (401)`); a stopped run sends nothing more. A run that asks a clarifying question is `suspended` until it is answered (R28): Plan `suspended` when it asked it, Analyse `suspended` when the agent asked it; the steps after it have not run yet and are not listed.
- A resume of a run that is not waiting answers 409 `Run "<id>" is not waiting for an answer`; a blank answer 400 `Answer is required`; another step 400 `Step "<stepId>" is not waiting for an answer`; a run that waited more than 30 minutes, or any waiting run after a restart, 410 `This run can no longer continue — run it again with your answer` (the run is then `stopped`, `waitingFor.expired`), all before any SSE frame (R28).
- A plan the model returns as anything but the JSON object plans nothing (the question as is, no clarification), unless its reply was cut at the output limit twice, which fails Plan (R43), and a clarification with fewer than 2 options is dropped; an answer that is not the JSON object is taken as the answer text, its first line the headline (R27).
- An analysis whose second attempt still fails Validate is answered anyway: Write answer gets the failed findings and says what they limit (R27).
- Starting a streamed run (or a follow-up) while 8 runs are running (or `WORKFLOW_MAX_LIVE_RUNS`) answers 429 `Too many runs are in progress (<n>). Wait for one to finish, or stop one.` and stores nothing; a resume is never refused, and a run waiting for the user or a draft run (Try it) does not count ([../../system/api.md](../../system/api.md) 119).
- A refused run (any R14 refusal, 404, 429) stores nothing. A run of a workflow that has since been removed keeps its workflow's stored name and stays listed, readable and deletable (R23).
- Reading, deleting or downloading from a run that doesn't exist answers `Run "<id>" not found` (HTTP 404); a file the run never showed answers the session routes' errors (`Panel item "<id>" not found`). Deleting a run while it runs answers `Stop the run before deleting it` (HTTP 400) and keeps it.
- A run whose turn reports nothing for 15 minutes (or `WORKFLOW_RUN_IDLE_MINUTES`) is aborted and stored `failed` with `The run made no progress for 15 minutes and was stopped`, its running step failed with it; its stream ends with `error { content }`. If its work does not unwind within 10 seconds of that abort, the run is stored so without it (R18); a Stop before then wins, and the run is stored `stopped`.
- Stop on a run whose work does not unwind within 10 seconds stores it `stopped` all the same and answers it, never `running`; when the work unwinds later the run stays `stopped`. Such a run can be deleted; if its work unwinds after that, nothing is stored again and its workspace and memory thread are deleted then (R16).
- If the app stops during a run, the run is listed `failed` with `The app stopped before the run finished` after the next start; the files its turn had written stay downloadable.
- A step whose output breaks its contract fails with, for example, `Contract violation in Analyse: calls[2].rowCount Invalid input: expected number, received string`; one whose input breaks it fails before it runs with `Contract violation in Receive question (input): datasets Invalid input: expected array, received string`; a whole value of the wrong kind names the path `(root)` (`Contract violation in Analyse: (root) Invalid input: expected object, received string`). The steps after it are `skipped` and the run is `failed` with the same error (R26). An agent turn's own failure keeps its own error.
- A workflow whose step requires a field nothing gives, gives with another type, or gives only maybe (an optional output or an optional input field without a default) never loads: the backend refuses to start with `Workflow "<id>" breaks its data contract: <step>.<field> <problem>; …`, each problem `not given by the input or an earlier step`, `expected <a>, got <b>` or `may be missing` (R26).
- A run stored before contracts existed has no `contractHash`; it reads as before (R26).
- A node chat refuses, before anything streams or is stored: an unknown run (`Run "<id>" not found`, 404), a blank message (`Message is required`, 400), a run still running (`The run is still running`, 409), a run waiting for an answer (`The run is waiting for an answer`, 409), a run of a removed workflow (`Workflow "<id>" not found`, 404), an unknown or code step (`Step "<id>" has no agent to chat with`, 400), a step that did not run (`Step "<id>" did not run in this run`, 400), and a second message while a reply about the same step is still being written (409). A failed turn stores its error with the message; a stopped one stores what came, marked stopped.
