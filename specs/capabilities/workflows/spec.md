# Workflows

Every run runs a **workflow**: a fixed sequence of steps defined in code, each one deterministic code or a call to an agent. The catalogue holds one workflow: **Answer a Business Question (Avery + Michael)** (`orchestrated-answer-michael`: Avery, the Chief of Staff, briefs Michael, who plans the analysis, queries the data and writes the answer; it is the only Answer a Business Question since 2026-11-23, when the user removed the fixed-line workflow `answer-business-question` and its orchestrated version `orchestrated-answer`, R48). The user removed **Dashboard Image to Artifact**, **Map a Dashboard to Data** and **Review a Website** on 2026-11-26 (R49), and **Consumption Gap Analysis** and **Assess Data Readiness** the same day (R50). Agents are no longer workflows: they are a library ([../agents-evals/spec.md](../agents-evals/spec.md)) that workflow steps call (workflows → agents → skills → tools), and they cannot be run from the Workflows area or from their own page. Workflows are read-only: the app never creates, edits or deletes one (ADR-0040, partly superseded by ADR-0042).

Every workflow is a **run workflow**: it runs once on a typed input defined in code and shows each step's result on its page; no chat can start (ADR-0041). Every run is stored: it is listed, reopened with its result and files, and deleted with them. A workflow's page is a designer: its graph on a canvas and one Run panel beside it (the Chat), with no right panel. The Run panel streams the run live and shows the answer with its provenance, and the user can stop it and answer its clarifying question (since 2026-11-20 the UI has no free follow-up: the composer shows only while no run is shown). The one-step agent workflows (`agent:*`), the Sequential test workflow (`seq-text-demo`) and Deep analysis (`deep-analysis`) were removed on 2026-11-12; the runs they stored stay readable (R23).

## Concepts

Defined in [../../product/glossary.md](../../product/glossary.md): workflow, code-defined workflow, agent, user agent, Live, session, workflow bar, workflow phase.

Capability-local vocabulary: a workflow's **id** (`orchestrated-answer-michael`), the agent a code-defined workflow runs for (its **primary agent**), its **trigger** (`run`), a workflow's **input** (its typed fields), a **run** (one execution of a workflow on an input), a run's **context** (one earlier run whose question and answer it is given), the **run host** (internal: the in-memory session a run's agent turn executes on) and a **legacy run** (a stored run of a workflow that is no longer in the catalogue, R23).

## Rules

The catalogue
- R1. The workflow catalogue SHALL list exactly one workflow: **Answer a Business Question (Avery + Michael)** (`orchestrated-answer-michael`, owner `Official`, since 2026-11-22; R45; [../../system/agents.md](../../system/agents.md) 5.23). It SHALL NOT list any agent: no System, Official, draft-only or Live user agent has a workflow of its own. Each entry SHALL carry its name, description, kind, owner, the agents its steps call, its number of steps, whether it takes the datasets the user picks, the datasets a session would take, the missing ones and the starter questions ([../../system/api.md](../../system/api.md) 116). A stored run keeps the workflow name it ran under. (Removed 2026-11-23, R48: **Answer a Business Question** (`answer-business-question`, until then first) and **Answer a Business Question (orchestrated)** (`orchestrated-answer`, until then second); the user removed both and kept Avery + Michael. Removed 2026-11-26, R49: **Dashboard Image to Artifact** (`recreate-dashboard`), **Map a Dashboard to Data** (`map-dashboard-data`) and **Review a Website** (`review-website`). Removed 2026-11-26, R50: **Assess Data Readiness** (`data-readiness-assessment`, until then second) and **Consumption Gap Analysis** (`consumption-gap-analysis`, until then third).)
- R2. The workflow's id SHALL be `orchestrated-answer-michael`. Any other id SHALL NOT resolve to a workflow, including the removed one-step ids `agent:assistant`, `agent:data-readiness`, `agent:<user-agent id>` and `agent:rfp`, the removed `seq-text-demo` and `deep-analysis` (2026-11-12), `answer-business-question` and `orchestrated-answer` (2026-11-23, R48), `recreate-dashboard`, `map-dashboard-data` and `review-website` (2026-11-26, R49), and `consumption-gap-analysis` and `data-readiness-assessment` (2026-11-26, R50).
- R3. Workflows SHALL be defined in code. The app SHALL NOT offer any control that creates, edits, reorders or deletes a workflow or a step, and the API SHALL have no write route for workflows. Publishing, editing or deleting a user agent SHALL NOT change the catalogue.

Sessions
- R4. Every session SHALL run one workflow. A session created from this version on SHALL store the id of its workflow at creation and never change it. A session saved before SHALL have its workflow derived at every read: a session of the removed Answer a Business Question keeps the id it was stored with, `answer-business-question` or `orchestrated-answer` (R48), as does one of the three workflows removed on 2026-11-26 (R49) or the two removed the same day (R50); a user agent (existing or deleted) and a plain session keep their internal `agent:<key or id>` reference as before (`agent:assistant` for a plain one), which is not in the catalogue and links to no workflow page; a session stored with `seq-text-demo` or `deep-analysis`, and one whose agent was Sarah (`agent:data-readiness`, removed, R50), reads as a plain Assistant session ([../../system/api.md](../../system/api.md) 2.1; [../../system/data-model.md](../../system/data-model.md) 3.4; [../past-chats/spec.md](../past-chats/spec.md) R65).

The Workflows pages
- R5. The **Workflows** area of the navigation rail ([../app-shell/spec.md](../app-shell/spec.md) R3) SHALL show the catalogue (R1) grouped by category (since 2026-11-23), one section per category headed by its name, in the order the category's first workflow comes in R1, each with its workflows in R1's order: **Data Analytics** (`data-analytics`: Answer a Business Question (Avery + Michael)); a workflow belongs to exactly one category, declared with it in code, and a category with no workflow has no section (`data-engineering`, `dashboards` and `software-development` have none since 2026-11-26, R49, R50). Above the sections, filter pills **All** (the default) and one per category, in section order, SHALL show only the picked category's section; the pills come from the whole catalogue, not the search, and reset with it each time the page opens. The workflow SHALL show its name, its description, its kind (`<n> steps`, `1 step` for a one-step workflow), `Uses <the names of the agents its steps call>` (Answer a Business Question (Avery + Michael): `Uses Avery, Michael, Clara`), its missing datasets (`Missing dataset: <names>`) and **Run** (R12); it has no Start chat. The page SHALL say, under its heading, `Each workflow runs on an input. Its steps call agent personas, and agent personas use skills and tools.` A search SHALL filter the list by name or description, ignoring case; when nothing matches, the page SHALL say `No workflows match "<query>"`.
- R6. Retired (1.23.22). **Start chat** is gone from every workflow card and page: chats can no longer be started. `POST /sessions` with a `workflowId` is refused with `Workflow "<id>" runs on an input`, creating nothing ([../../system/api.md](../../system/api.md) 3). Past chats stay readable ([../past-chats/spec.md](../agent-answers/spec.md) R66).
- R7. A workflow's page SHALL show, in its Builder view (R38; the page opens in Business by default), an n8n-style **designer** (since 1.23.10; left to right since the n8n-style page): a header with the breadcrumb `Workflows / <name>` (its first part goes back to the Workflows page), the name, id, kind and missing datasets, and no action; the workflow's **graph** on a canvas, left to right on one centre line (a Start node, one node per step with its title, id and kind badge `CODE` or `LLM`, an agent step's action, then its own agent's persona name and job title (Orchestrate: Orchestrate, Avery, Chief of Staff, with Michael and Clara hanging under her), its model and, when it has tools, one Tools sub-node (`<n> tools`) under it, an End node, and between them connectors labelled with the number of fields each passes on, as `GET /workflows/:id` returns them), fitted to the canvas when it opens (at most 100%, and at least 70% while the graph's full height shows, never below 40%; laid out roomy rather than packed, so a long graph opens at 70%, panned sideways, and a run pans to each node as it starts running), with zoom (50%–150%), reset and fit to screen, and **Run workflow** at its top-right (R12); the canvas takes the column's full height (the **Logs** panel under it was removed on 2026-11-16: its list repeated the canvas and its detail the node dialog) and on the right one **Run** panel (resizable from its left edge, maximizable, folding to a narrow strip): in its header the run's status, `<n> of <m> nodes ran` (Start and End count), its duration and run id, and the run's activity line, and in its body the **Chat** (the question, the run's answer and the composer, R12, R13); while a run is shown each node carries its live state (R13) and a code step its run line, and once the run has ended **How it ran**, under the answer, reads it step by step. The app's right panel SHALL NOT be shown on a workflow's page (no `Expand right panel` button), and opening a workflow SHALL NOT open it; its open state is kept for the other views (app-shell R9). Clicking a node SHALL select it on the canvas; double-clicking it (or Enter) SHALL open its **node dialog**: its Input, its Parameters and Settings, and its Output in the run shown (Start: the description, trigger, output fields, input parameters and agents (R8); a step: id, kind, agent, model, tools, max steps, exits, what it receives and returns and the job description of the step's own agent: Avery's for Orchestrate). A click, double click or Enter on the **Tools** sub-node SHALL open a keyboard-navigable list of its tools (Escape closes it), and picking a tool SHALL open that tool's dialog, not its agent step's: its name, description and input parameters (`GET /workflows/:id` `agents[].toolDetails`), its agent and step, and, in the run shown, each of its calls in that step with its input (the SQL) and result, their count, total duration and the run id; the agent's system prompt SHALL NOT appear in it. The Model sub-node SHALL open its agent step's dialog. Workflows SHALL stay the current rail item while the page is open. The agent detail's Graph tab keeps its own drawing ([../agents-evals/spec.md](../agents-evals/spec.md) R108).
- R8. A workflow's Start node dialog SHALL list, under **Agent personas**, each agent its steps call (for Answer a Business Question (Avery + Michael): Avery, Michael and Clara), and an agent step's dialog SHALL link its own agent: its Agent link opens that agent's detail. Choosing one SHALL open that agent's detail ([../agents-evals/spec.md](../agents-evals/spec.md) R5).
- R9. The Workflows page SHALL read the catalogue each time it opens. Opening a workflow that is not in the catalogue SHALL show `Workflow "<id>" not found` on its page.
- R10. Retired (1.23.22). The Workflow tab no longer carries the workflow bar note (`In a chat, the workflow bar shows …`): no chat runs a workflow, so no bar follows it.

Run workflows
- R11. Every workflow SHALL have the trigger `run` (since 1.23.22; `chat` is gone). A workflow SHALL declare its input in code: typed fields, each with a name, a label, a type (`text`, `textarea` or `number`; R14 adds `boolean` and `datasets`), whether it is required and an optional placeholder. The catalogue SHALL carry each workflow's trigger and input ([../../system/api.md](../../system/api.md) 116). Running a workflow SHALL run its steps once along its flow (its edges, R27) on the input and answer each step's status (`success`, `failed`, `stopped` or `skipped`) and output, and the final output; a failing step SHALL make the run failed with that step's error, and the steps after it SHALL be skipped ([../../system/api.md](../../system/api.md) 118). A required field that is missing, empty or whitespace-only SHALL be refused with `<label> is required`, and a number field that is not a number with `<label> must be a number`, running nothing. A run SHALL NOT be a session: it writes no workflow bar and is never listed with the sessions; it is stored as a workflow run (R18). A workflow without input fields SHALL NOT be run (`Workflow "<id>" can't run on an input`), and no workflow can start a chat (`Workflow "<id>" runs on an input`, creating nothing).
- R12. A workflow's card SHALL show its kind (R5) and **Run**, which opens its page. A workflow's page SHALL show **Run workflow** on its canvas, which unfolds the **Run** panel and focuses the composer's text box, and never runs by itself: the Chat's **composer**, a pill bar (since 2026-11-22, R47) with a `+` button for the optional inputs, a text box and **Send**, which is disabled while the run is going; the Chat is a conversation, not a form, and the agent asks for any required input that is missing (R47). Its Start node dialog SHALL list the input fields as its input parameters (name, label, type, `required`), and Agents only when its steps call one.
- R13. After a run, the Run panel's Chat SHALL show the question asked (with a thumbnail for each reference image the run was given, R35), then `Run succeeded` or `Run failed: <error>` and the run's answer (for Answer a Business Question (Avery + Michael), with the query chips, the coverage line and the query rows of R31 in place of `How I worked this out` and `Data used`) or final output field by field; there SHALL be no per-step result cards and no separate run-progress list. Once the run has ended, **How it ran**, under the answer, SHALL read it step by step: the run's figures, then each step (Start and End aside) with its state, its duration and its story's headline, the title opening its dialog; while the run is shown, each node on the canvas SHALL carry its status as a badge (`×<n>` when it ran more than once), a code step its run line (its story's few words and its duration), each connector leaving a `Done` node SHALL be marked done, and each node's dialog SHALL show its Story and what the node received (its input) and produced in that run, its duration and, for an agent step, its tool calls; a failed node shows its error in its Output. A refusal SHALL be shown as an agent message in the Chat with the server's message (`Question is required`) or `Backend unreachable`. Running again SHALL replace the run shown, and leaving the page SHALL discard it, except a run still queued, running or waiting for the user: leaving SHALL NOT stop it (R16; ADR-0048), and opening its workflow again SHALL show it once more, as it is then (a queued run with the status line `Queued…` and its nodes idle); a running run SHALL be followed again with its live view rebuilt from its events so far (the steps, the Thinking, each tool call, the answer forming; [../../system/api.md](../../system/api.md) 149) and go on live to its end. Opening a running run from Runs, or from its background task, SHALL do the same on its workflow's page. While it is queued or runs, every run (started here, resumed, queued, or found queued or running when the app starts, [../../system/api.md](../../system/api.md) 120) SHALL be a `workflow-run` background task (app-shell R58-R63), titled `<workflow name>: <question>`, `Waiting for a free slot` while it is queued, `Waiting for you` while it waits for the user, whose Open shows it as above and whose Stop stops it (150); its end is toasted only when the page does not show it, never for a stopped run.

Runs (ADR-0041; backend only in 1.23.12)
- R14. The workflow SHALL declare its input in code, with the field types `text`, `textarea`, `number`, `boolean` (a checkbox; absent means false), `datasets` (one or more dataset names), `image` (one PNG, JPEG or WebP image) and `images` (reference images, up to 4; R35), each field optionally with a default, a datasource-kind limit and a hidden flag ([../../system/api.md](../../system/api.md) 116): Answer a Business Question (Avery + Michael) takes `question` (at most 4000 characters) and `datasets`. A field MAY carry rules: `maxLength` (text), `min` and `max` (number). A run's input SHALL be checked as a whole, in field order, before anything runs (R24), every refusal reported (at most one per field): `<label> is required`, `Select at least one dataset`, `<label> must be a number`, `<label> must be at least <n>`, `<label> must be at most <n>`, `<label> must be at most <n> characters`, `<label> must be true or false`, `<label> must be PNG, JPEG or WebP images`, `<label> must be at most 5 MB each`, `<label> must be at most 4 images` (R35), `Dataset "<name>" not found`, `Dataset "<name>" is not a <kinds> dataset`; a missing, empty or whitespace-only required text (a blank question) SHALL be refused with `<label> is required`; unknown keys SHALL be ignored. The refusal SHALL carry the first error as its message and every error with the field it is about ([../../system/api.md](../../system/api.md) 118).
- R15. A run of Answer a Business Question (Avery + Michael) SHALL run Avery's turn on the run's input (R45): each of Michael's analyses (`answer_from_data`) is an agent turn with the same model request a chat turn sent for the same question over the same datasets (plus the catalog block and Avery's brief): clarification and panel items SHALL behave as they did in a chat turn. Its answer SHALL be Michael's written answer followed by Avery's closing words (R45), and no grounding guard or tool-only synthesis SHALL rewrite it. Its run host SHALL exist only for the run: created when it starts, never listed with the sessions, its memory thread deleted and itself discarded when it ends; its workspace stays with the run.
- R7a. An agent step on the workflow page SHALL show who does it as a person: the agent's portrait and an `AI` badge on its canvas node and, while a run is shown, what the agent is doing in place of its job title; the Run panel SHALL show the run's agents as a team, each with a first-person sentence about its part and the handoff from the agent before, built only from the run's step data, never by a model ([ui.md](../../system/ui.md) 4.4b, *Agents at work*). A step's queries SHALL stay reachable from its row through its dialog and the query inspector. Each agent's work SHALL show under that agent, in plain words (its own reason for each tool call, else a phrase for the tool, never the tool's name), with at most one step marked as under way, and the agents still waiting SHALL share one `Up next` line (2026-11-17).
- R16. A streamed run SHALL report, in order: that it was accepted (its run id) and, when no slot is free, that it is queued (`queued`, R19b), then, once it starts, each step's start and end with its status (`running`, then `success`, `failed`, `stopped`, `suspended` for a step that waits for the user's answer (R28), or `skipped` for a step that never ran: the branch not taken, or the steps after a stop or a failure) and output, a step that runs more than once with its `attempt` (1, then 2 when it runs again), the agent turn's events exactly as the chat stream sends them (its `text` being the answer, streamed by Avery's turn), and one terminal event: the run with its answer, steps, output, datasets, panel items, visuals, or the chat stream's error for the same failure; a run that waits for the user sends the waiting step's `suspended` end and what it waits for (`input-required`) before the terminal event, the run then `suspended` ([../../system/api.md](../../system/api.md) 119, 138, 3.6). A refusal SHALL answer its real status before anything streams. A run (started or resumed) SHALL run on the server detached from the connection (ADR-0048): closing the connection, leaving the page, reloading or closing the window SHALL NOT stop it; each event SHALL carry its number (`seq`), and any client SHALL be able to follow the run again from its events so far, then live, until 10 minutes after it ends ([../../system/api.md](../../system/api.md) 149). **Stop** ([../../system/api.md](../../system/api.md) 150) on a queued run SHALL store it `stopped` at once (no steps, `Run stopped`) and take it out of the queue. **Stop** SHALL stop a running one as Stop stops a chat turn: the agent turn aborts, nothing more of it is sent, the run ends `stopped` with any partial answer, and its stream ends with the stopped run; Stop on a run that ended answers it as it is. Stop SHALL always end the run: when the work has not unwound 10 seconds after the stop, the run SHALL be stored `stopped` without it (its running steps `stopped`) and its stream ended with that run, and the work's later unwind SHALL NOT change that status (it may add the partial answer) and SHALL send nothing more. Try it (agents-evals R60) and a step's chat (R25) keep stopping when their connection closes.
- R17. A run MAY name one earlier run as its context: that run's question and answer SHALL reach the agent before this run's question, as a user and an assistant message, and nothing else of it; its own context SHALL NOT be carried. The earlier run SHALL be read from the stored runs (R18), so it can be named after the app restarts. A context naming no stored run SHALL be refused with `Run "<id>" not found`, and one without an answer with `Run "<id>" has no answer to continue from`, except a run that waited for an answer it can no longer take (R28: **Run again with my answer**): its question and the clarifying question it asked (with its options, one `- <option>` line each) SHALL be the context, so the new run's question, the user's answer, is planned with the original question. Since 2026-11-20 the app's UI no longer offers a free follow-up (no follow-up form, no agent picker): only the app itself sends this context, where it still applies, for an answer's clarification option and for **Run again with my answer** (R28); the API rule is unchanged.

Stored runs (1.23.14; the run history UI is 1.23.21)
- R18. Every run of a workflow on an input, streamed (119) or not (118), SHALL be stored when it is accepted, as `queued` (a run of 118 runs inline and is stored `running`; it takes no slot and is never queued) with its workflow, the workflow's name, its checked input and its context, then `running` when a slot is free and it starts (its `attempts` counting the starts, R19b), its steps updated at each step change while it runs (the steps so far, the running one with its tool calls; a failed write of them never fails the run), and updated when it ends with its status (`success`, `failed` or `stopped`), every step's status and output, its output or error and its question, answer, datasets, agent, panel items, visuals and the agent's saved phases ([../../system/data-model.md](../../system/data-model.md) 3.16). A stopped run (Stop, [../../system/api.md](../../system/api.md) 150; never a closed connection, R16) SHALL be stored `stopped` with any partial answer; a run that fails while ending SHALL be stored `failed` with that error. A run that makes no progress SHALL be ended: a turn (119, 118, 138, Try it) that reports no event at all for 15 minutes (`WORKFLOW_RUN_IDLE_MINUTES`, at most 35791, the longest a timer holds; `0` turns it off) SHALL have its work aborted and be stored `failed` with `The run made no progress for <n> minutes and was stopped`, its running step failed with the same error, any partial answer kept, its stream ending with that error; it is never `stopped`, which is the user's Stop. A run waiting for the user, and a queued run, are never timed: the watchdog times only running time. A run's workspace SHALL stay with the stored run, so its files can be downloaded after the run, and after a restart. A run's live state (its stop signal and event log) lives in server memory only: a backend restart queues a running run again as R20 says.
- R19. The Runs page's **Runs** tab (app-shell R46) SHALL show the run history and a row SHALL reopen its stored run (roadmap 1.23.21): a run whose workflow is still in the catalogue SHALL open on **its workflow's page, drawn with that run** (a run still queued or running followed there live, R13; ADR-0048) (each node's status on the canvas, How it ran, the node dialogs with each step's input and output, the Run panel's Chat with its question, its answer or waiting card, its visuals, and node chats, as after a run on the page), the composer hidden while the run is shown (R21); a legacy run (R23) SHALL open read-only (`run-detail`, with no Run again). On the page, **Run again** (shown with a run, not while one runs) SHALL clear the run shown and bring the composer back with that run's whole input, its question too, to change and Send as a new run; the run stays stored. The run history SHALL list every stored run, newest first, optionally one workflow's, each with its workflow, its status, its start and end, and a title: its question, else the workflow's first text input with a value, else the workflow's name, at most 120 characters ([../../system/api.md](../../system/api.md) 120). A stored run SHALL be readable with its full result, the panel items, workflow view and agent derived as a session's are (121), and its visuals and panel files SHALL download as a session's do (123-126). An unknown run SHALL answer `Run "<id>" not found` (HTTP 404).
- R19b. A streamed run (119) SHALL never be refused for the number of runs in progress (ADR-0057): at most `WORKFLOW_MAX_LIVE_RUNS` (default 8) runs are `running` at once and any other accepted run SHALL wait `queued`, stored with `queuedAt`, its stream sending `run` then `queued`. When a slot frees, the oldest queued run (by `queuedAt`) SHALL start: stored `running`, `attempts` counting its starts, prepared again from its stored input, context and images (a follow-up gets a fresh transcript; when that is refused because its dataset or workflow is gone, the run ends `failed` with the refusal's message). A queued run SHALL keep its id and conversation, SHALL be followed (149) and stopped (150) like a running one, and counts as active: it SHALL NOT be deleted, archived, visualised, inspected or chatted about until it ends. A run of 118 and a resume (138) are never queued.
- R20. Deleting a run SHALL remove it, its workspace and its files, its agents' memory threads (R30) and its node chats with their threads (R25) (122: `Run deleted`). A run still queued or running SHALL NOT be deleted (`Stop the run before deleting it`). When the app starts, a run left `running` SHALL be queued again and start from scratch once the app is up (ADR-0057): `queued`, its steps, output, error and answer cleared, its memory threads deleted, its workspace inputs kept, at most 3 starts (`attempts`); a run cut off after its third start SHALL become `failed` with `The app stopped before the run finished`, keeping its workspace, its memory threads and the steps it finished, its running step (or a step stored waiting before the run was stored waiting) `failed` with the same error; queued runs stay queued and are started oldest first; every registered workflow's leftover suspended snapshots SHALL be deleted; and a run workspace that no stored run owns SHALL be deleted. The start-up clean-up of the agent editor's previews SHALL NOT touch run workspaces.

Runs from a workflow's page (1.23.15)
- R21. Every workflow (Answer a Business Question (Avery + Michael)) SHALL offer **Run workflow** and the **Run** panel on its page (no Start chat). Before a run the Chat SHALL show the workflow's name, a one-line hint built from its agents and the starter questions (R47). The composer SHALL be the pill of R47 (since 2026-11-22): a text box for the question (Enter sends, Shift+Enter adds a line), a `+` button whose popover holds the optional inputs (the dataset picker for `datasets`, reference images when the workflow declares an `images` field, an artifact, other optional pickers or text, and each `boolean` as a switch, checked when its default is true) and **Send**; a required input still empty is asked by the agent in the chat, not by a form field. The composer SHALL show **only while no run is shown** (2026-11-20): while a run is running, waiting for the user (a clarifying question) or ended, the conversation takes the whole column. **Stop** SHALL sit in the Chat's top bar, shown while a run is queued or running. **New question** (shown with a run, not while it runs) SHALL clear the run shown and the question, keep the datasets (a run opened from Runs: its datasets and other fields) and bring the composer back, focused; **Run again** beside it keeps the question too (R19). Every run from the page SHALL stream ([../../system/api.md](../../system/api.md) 119): the status `Queued…` while the run waits for a slot (R19b), then `Running…` in the Chat and each step's status live on its canvas node (`Running`, then `Done`, `Failed`, `Skipped` or `Stopped`), and inside a running agent step the agent's Thinking, each tool call with its rows and the answer forming in the Chat; when it ends, the run as stored: its status line and its answer as a chat shows one (text, reasoning, interpretation, data with its SQL, badges, visual, the clarification card), each step's data in its node dialog. **Stop** SHALL stop the run on the server ([../../system/api.md](../../system/api.md) 150) and drop the stream; the run reads `Run stopped`, its running step `Stopped`, and is then shown as stored, with any partial answer (Stop before the run has its id stops it as soon as it has one). The Chat SHALL NOT offer a free follow-up (decided 2026-11-20: "the follow-up question is useless since it was removed"): no `Follows up on this run` form, no follow-up question box, no agent picker and no **Follow up** button. Picking a clarification option (or `Something else`, or Skip) SHALL start a run with the pick as the question and the shown run as its context (R17), saying `Follows up on “<earlier question>”`. When the user asks Avery to export, download or share the conversation (as a PDF, a PowerPoint, slides, a deck or a presentation; in English or Spanish), she SHALL export the **whole conversation**, every earlier question of it with her answer, in one call of `export_conversation`, and SHALL NOT call the team to analyse again. The tool SHALL be offered **only on such a request**: otherwise Avery SHALL NOT have it, its skill or its instructions, and her run's facts SHALL NOT mention an export, so any other message is answered exactly as before. She SHALL write the file's title, a summary of 2 to 5 findings and one headline per earlier question in the conversation's language, and every figure she writes SHALL be one an answer of the conversation gave: a figure that is not SHALL be refused before anything is made, and she SHALL fix it and call once more (at most twice per run). The **PDF** SHALL hold a cover, the summary with the conversation's questions, each question with her full answer and its dashboard, and an appendix of the queries (their SQL only when the user asks for it); the **PowerPoint** SHALL hold the same as native text and tables, the answer in each slide's notes. A dashboard SHALL be drawn as the app draws it, one image per row of widgets, its table widgets as tables; its latest version in full, each earlier version as its first row with `Version <n>, replaced by version <m>`. Both SHALL be drawn with the computer's own Microsoft Edge or Google Chrome; without one Avery SHALL say `Exporting needs Microsoft Edge or Google Chrome on this computer.` The run's answer SHALL carry the export (`answer.export`), shown as an **export card** with one download per file ([../../system/ui.md](../../system/ui.md) 4.4b); the files SHALL stay downloadable (167) after the run.
  - **Models** (2026-11-19, 2026-11-22; [../../system/agents.md](../../system/agents.md) 1.3). When the saved model is served as a Claude model, Avery SHALL run on `claude-opus-5-5` at reasoning effort `high` and Michael on `claude-opus-5-5` at `medium`, in runs, never in evals; otherwise both run on the saved model and effort. Everything this rule and R46 say holds for the workflow's step, exits, wait, conversation and archive.
- R46. **Avery's conversation** (2026-11-20; R45). A conversation with Avery SHALL never end unless it is archived. The same holds for a conversation with Elena, the Insights Lead ([agents-evals](../agents-evals/spec.md) R115; [../../system/architecture.md](../../system/architecture.md) ADR-0058), whose messages are runs of `agent:insights-lead` instead of `orchestrated-answer-michael`: one conversation path serves both ([../../system/agents.md](../../system/agents.md) 5.14). The rules below are written for Avery:
  - **Runs and conversations.** Each message to Avery SHALL be a run of `orchestrated-answer-michael`. A run with no `context.fromRunId` SHALL start a conversation: its `conversationId` is its own id. A follow-up (`context.fromRunId` naming an earlier run, [../../system/api.md](../../system/api.md) 118, 119) SHALL join the earlier run's conversation (the same `conversationId`) and Avery SHALL read the conversation so far: the questions and answers of its runs in order, the **last 20 turns**, as the host's transcript, then the new message ([../../system/data-model.md](../../system/data-model.md) 3.16).
  - **The run chat** ([../../system/ui.md](../../system/ui.md)) SHALL show, for this workflow, a **Message Avery** box under her last reply that sends the text as a follow-up, and **Archive** in the chat's top bar. While she works the box SHALL stay, with **Stop** in it, and what the user sends SHALL be queued and sent, oldest first, each when the answer before it ends. The chat's top bar SHALL always offer **Export** (PDF and PowerPoint, PDF only, PowerPoint only) in an open conversation, which asks Avery for the export as a message of the conversation.
  - **Archive.** Archiving ([../../system/api.md](../../system/api.md) 159) SHALL set `archivedAt` on every run of the conversation. An archived conversation SHALL be hidden from the run history (120, which keeps its 120-character titles) and from the home page's recent runs, SHALL be read-only (no Message Avery box, no Run again) and SHALL be listed on the Runs page under an **Archived** filter (120 `?archived=true`), where **Unarchive** (160) brings it back. A message to an archived conversation SHALL be refused with 409 `This conversation is archived`; archiving while a run of the conversation runs or waits SHALL be refused with 409 `The run is still running`; an unknown run answers 404.
  - The archive is a flag: nothing is deleted, and deleting a run (122) works on an archived one as on any other.
  - **The dashboard travels with the conversation.** The dashboard of a conversation SHALL be the one on its last answer that carries one: a later message of the conversation SHALL be handed that dashboard (R45), so asking for a change in plain words is enough, and archiving the conversation SHALL keep its artifact. Deleting the artifact SHALL end the carry: the next message is read on its own words.

## Edge cases and errors

- Opening a workflow that is not in the catalogue (unknown, draft-only, System or a primary agent) answers `Workflow "<id>" not found` (HTTP 404).
- Starting a chat with any workflow is refused with `Workflow "<id>" runs on an input`, whatever the id, creating nothing (R6).
- Starting a chat with a workflow in the catalogue is refused with `Workflow "<id>" runs on an input`, creating nothing (R6); an id that is not in the catalogue answers `Workflow "<id>" not found` first.
- A removed workflow id (`agent:assistant`, `agent:data-readiness`, `agent:<id>`, `seq-text-demo`, `deep-analysis`) answers `Workflow "<id>" not found` (HTTP 404) on read and on run. A user agent's draft preview (Try it) is not a workflow run ([../agents-evals/spec.md](../agents-evals/spec.md)).
- Running a workflow without input fields answers `Workflow "<id>" can't run on an input` (HTTP 400). Running Answer a Business Question (Avery + Michael) without a question (or with a whitespace-only one) is refused with `Question is required`, and with a question but no datasets with `Select at least one dataset`; with neither, with both errors at once (R24).
- A run whose agent turn fails ends with the chat stream's error for the same failure (a custom endpoint's `The endpoint rejected the API key (401)`); when it is Michael's model call that fails, Orchestrate fails with `Michael (Insights Analyst) could not answer: <that error>`, never a success with an empty answer; a stopped run sends nothing more. A run that asks a clarifying question is `suspended` until it is answered (R28): Orchestrate `suspended` when Avery asked it; the steps after it have not run yet and are not listed.
- A resume of a run that is not waiting answers 409 `Run "<id>" is not waiting for an answer`; a blank answer 400 `Answer is required`; another step 400 `Step "<stepId>" is not waiting for an answer`; a run that waited more than 30 minutes, or any waiting run after a restart, 410 `This run can no longer continue — run it again with your answer` (the run is then `stopped`, `waitingFor.expired`), all before any SSE frame (R28).
- Starting a streamed run (or a follow-up) while 8 runs are running (or `WORKFLOW_MAX_LIVE_RUNS`) is never refused: it is stored `queued`, its stream sends `queued`, and it starts when a slot frees, oldest first; a resume is never queued, and a run waiting for the user or a draft run (Try it) does not count ([../../system/api.md](../../system/api.md) 119). Stop on a queued run stores it `stopped`, no steps, `Run stopped`.
- A refused run (any R14 refusal, 404) stores nothing. A run of a workflow that has since been removed keeps its workflow's stored name and stays listed, readable and deletable (R23).
- Reading, deleting or downloading from a run that doesn't exist answers `Run "<id>" not found` (HTTP 404); a file the run never showed answers the session routes' errors (`Panel item "<id>" not found`). Deleting a run while it is queued or runs answers `Stop the run before deleting it` (HTTP 400) and keeps it.
- A run whose turn reports nothing for 15 minutes (or `WORKFLOW_RUN_IDLE_MINUTES`) is aborted and stored `failed` with `The run made no progress for 15 minutes and was stopped`, its running step failed with it; its stream ends with `error { content }`. If its work does not unwind within 10 seconds of that abort, the run is stored so without it (R18); a Stop before then wins, and the run is stored `stopped`.
- Stop on a run whose work does not unwind within 10 seconds stores it `stopped` all the same and answers it, never `running`; when the work unwinds later the run stays `stopped`. Such a run can be deleted; if its work unwinds after that, nothing is stored again and its workspace and memory thread are deleted then (R16).
- If the app stops during a run, the run is queued again after the next start and runs from scratch (ADR-0057): the steps and answer of the cut-off attempt are gone and its `attempts` goes up; after its third start is cut off it is listed `failed` with `The app stopped before the run finished` and the files its turn had written stay downloadable. If a queued run can no longer be prepared (its dataset or workflow was removed), it ends `failed` with the refusal's message.
- A step whose output breaks its contract fails with, for example, `Contract violation in Explain report: calls[2].rowCount Invalid input: expected number, received string`; one whose input breaks it fails before it runs with `Contract violation in Resolve dataset (input): datasets Invalid input: expected array, received string`; a whole value of the wrong kind names the path `(root)` (`Contract violation in Explain report: (root) Invalid input: expected object, received string`). The steps after it are `skipped` and the run is `failed` with the same error (R26). An agent turn's own failure keeps its own error.
- A workflow whose step requires a field nothing gives, gives with another type, or gives only maybe (an optional output or an optional input field without a default) never loads: the backend refuses to start with `Workflow "<id>" breaks its data contract: <step>.<field> <problem>; …`, each problem `not given by the input or an earlier step`, `expected <a>, got <b>` or `may be missing` (R26).
- A run stored before contracts existed has no `contractHash`; it reads as before (R26).
- A node chat refuses, before anything streams or is stored: an unknown run (`Run "<id>" not found`, 404), a blank message (`Message is required`, 400), a run still queued or running (`The run is still running`, 409), a run waiting for an answer (`The run is waiting for an answer`, 409), a run of a removed workflow (`Workflow "<id>" not found`, 404), an unknown or code step (`Step "<id>" has no agent to chat with`, 400), a step that did not run (`Step "<id>" did not run in this run`, 400), and a second message while a reply about the same step is still being written (409). A failed turn stores its error with the message; a stopped one stores what came, marked stopped.
