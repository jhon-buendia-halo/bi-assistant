# M1-22 — Sampled profiling and synthetic data

- **Jira:** none (repo only; epic id M1-22) · **Roadmap:** Milestone 1.22 · **Status:** Confirmed (2026-11-11)

## Goal

A user can profile the tables of a PostgreSQL or Databricks dataset quickly, from a sample of their rows, and then download a synthetic copy of them as a SQL script in the datasource's own dialect.
- The profile shows types, null rates, distinct counts, ranges, categorical values and text patterns.
- The copy keeps each column's distribution, null rate and format, and keeps primary and foreign keys consistent.
- The copy never carries a real identifier, name or free-text value.

The user can do this from the dataset editor or by asking the Data Readiness Agent in chat. Why: realistic test, demo and development data without exposing the real data, and a fast first look at a dataset without a full readiness assessment.

## Scope

- **Sampled profile (separate from readiness).**
  - Up to 1,000 rows per table are read with the engine's native sampling (`TABLESAMPLE … REPEATABLE` on PostgreSQL and Databricks). Small tables are read whole, and tables that refuse sampling fall back to their first rows.
  - The profile holds approximate statistics and character-class patterns, never raw rows.
  - Real values appear in it only for low-cardinality categorical columns (at most 20 distinct values, each seen at least 3 times).
  - It is computed on demand, kept in memory for 60 minutes so a script can be generated from exactly what the user saw, and never stored.
  - The Data Readiness assessment, its exact statistics and its scores do not change, and a sampled number never feeds a score.
- **Generator.** Deterministic and seeded, with no LLM: the same profile and request always give the same script.
  - Keys are generated first, so every foreign key resolves, cycles included.
  - Each column is generated by a strategy chosen from its kind: sequence, UUID, unique pattern, foreign key, categorical reuse, numeric or temporal range, boolean rate, format template, text pattern, placeholder words, or NULL for types it cannot synthesize.
  - The user picks the rows per table: default 100, at most 10,000, at most 200,000 per script.
- **Script.** A UTF-8, LF-only `.sql` file the user downloads.
  - It holds a header of what was generated, `CREATE SCHEMA` of a target schema (default `synthetic`), `CREATE TABLE` per table, batched `INSERT`s and, optionally, key and foreign-key constraints.
  - It is written in PostgreSQL or Databricks SQL, after the dataset's datasource.
  - The app never runs it: datasources stay read-only.
- **Dataset editor.** A third tab, **Profile & synthesize**, on a saved dataset: pick tables, profile a sample, read the profile, set rows, seed and target schema, and download the script.
- **Data Readiness Agent.** Two tools, `profile_data_sample` and `generate_synthetic_data`, call the same service. The script is saved in the session and shown in the panel for download. Prompt rule D12 is widened and D14 added.
- **API.** `POST /synthetic-data/profiles` and `POST /synthetic-data/scripts`.

## Out of scope

- Loading synthetic data into any datasource, or any write path to a datasource.
- REST datasources, and dialects other than PostgreSQL and Databricks SQL (no cross-dialect export).
- Storing profiles or scripts outside the chat session workspace, and profile history.
- Changing readiness profiling, scoring or rule R29 (exact aggregates, no sampling).
- LLM-written data, semantic generators (realistic person names, addresses), locale-aware text and differential-privacy guarantees.
- Preserving cross-column correlations beyond keys (for example city ↔ country); columns are generated independently.
- Configurable sample size above 1,000 rows, or configurable categorical thresholds.

## Acceptance

- On World Cup (PostgreSQL), Profile & synthesize profiles every table in seconds and shows each table's sampling method and each column's statistics and strategy.
- The downloaded PostgreSQL script loads into an empty database with every requested row and every foreign key valid, and the same seed gives the same SHA-256.
- A Databricks dataset downloads a Databricks SQL script that passes the writer's golden tests and, if the user agrees (open question Q1 of the plan), one live run in a scratch schema.
- No non-categorical sampled value appears in a profile or a script (privacy specs). Categorical columns reuse their real values.
- The readiness engine, profiling statements and scores are unchanged: their golden and score-equality specs are green and data-readiness R29 is untouched.
- In a Data Readiness session, asking for synthetic data puts a downloadable `.sql` file in the panel. The Data Readiness evals pass at 100 % over 3 runs.
- `check-specs`, backend and frontend unit tests, lint, builds and the impacted Playwright specs are green.

## Dependencies, risks and open questions

- **Depends on** the readiness profilers' pooled sessions (ADR-0031, ADR-0033), the dataset editor tabs (1.21.8), `show_in_panel` file items and their download (ADR-0029), and the tool-services bridge pattern.
- **Risk: sampling cost on large Databricks tables and views.** Mitigated by timing the statements live on a small and a large real table before integration (1.22.1), the per-statement timeout, and falling back to a first-rows read.
- **Risk: Databricks script correctness without a CI warehouse.** Golden tests, a statement smoke check and one live run.
- **Risk: privacy by construction.** Only categorical values are reused, and the real minimum, maximum and 11 quantiles of numeric and temporal (non-identifier) columns can appear; identifier columns carry none. Both are stated in the capability spec and tested.
- **Decided Q1 (2026-11-11):** the 1.22.3 gate runs one generated Databricks script once, pasted by the user into the SQL editor against a scratch schema of their workspace; the app itself never writes.
- **Decided Q2 (2026-11-11):** scripts generated in chat keep the 256 KB panel-file limit; larger requests are refused with a pointer to the dataset editor.
